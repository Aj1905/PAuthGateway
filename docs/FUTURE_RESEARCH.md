# 追加研究の候補

本書は、現行の論文計画(`paper/PAuthGateway/AUTHORING_GUIDE.md`)の範囲外と判断した
が、将来の研究として検討価値のある候補を記録する。各候補には「なぜ今やらないか」
を必ず残す。採用を決めた時点で、参照論文は `paper/README.md` の規則に従って
`references.bib` とフォルダに正式に追加する(それまでは bib に入れない)。

記載の型: 概要 / 根拠 / なぜ今やらないか / 着手の条件。

## 1. τ-Knowledge を注入経路として使う RAG 攻撃面の評価

- **状態**: 見送り(2026-08-01 判断)。`paper/` にも bib にも未追加。
- **参照**: τ-Knowledge — Quan Shi, Alexandra Zytek, Pedram Razavi, Karthik
  Narasimhan, Victor Barres,「τ-Knowledge: Evaluating Conversational Agents over
  Unstructured Knowledge」, arXiv:2603.04370, v1 = 2026-03-04, 査読なし
  (2026-08-01 時点)。タスク実体は tau2-bench リポジトリの banking_knowledge
  ドメイン(τ³-bench 系、`paper/Tau3Bench/README.md` 参照)。
- **概要**: τ-Knowledge は約700件の相互リンクされた社内文書を検索しつつ、口座更新
  などツール経由の状態変更を行う能力ベンチマーク。この検索対象文書を信頼できない
  入力とみなし、文書内に注入した指示が認可境界を越える操作を誘発できるか、
  gateway がそれを止められるかを測る攻撃面評価に転用できる可能性がある。
  検索文書は AgentDojo のツール応答とは別種の注入経路であり、本プロジェクトの
  防御主張の適用範囲を広げる余地がある。
- **なぜ今やらないか(2026-08-01 の判断、3点)**:
  1. 基線が低すぎる。最先端モデルでも合格率約 25.5% で、試行反復で信頼性が急落
     する。素の失敗が 75% を占める環境では、可用性低下を gateway に帰属できない。
  2. 失敗の型が認可と直交する。主要因は検索ミスと内規の読解ミスであり、
     過剰権限・権限不足という本プロジェクトの評価軸を測れない。攻撃部品も
     標準では含まれない(能力ベンチであり安全性ベンチではない)。
  3. 成果物が不安定。banking_knowledge の採点は tau2-bench release v1.0.1
     (2026-07-22)で修正されたばかりで、リリースノート自身が「スコアは release
     をまたいで比較不能(pass^1 が最大約9ポイント動く)」と明記している。
- **着手の条件**: (a) 注入部品(文書への指示埋め込みと成否判定)を自作する工数を
  新規研究として正式に確保する — これは既存ベンチの流用ではなく AutoDojo 型の
  拡張に相当する。(b) 採点が安定した release を固定できる。(c) 基線の低さへの
  対処として、攻撃成功率のみを測り可用性測定は諦める、という測定設計の割り切り
  を受け入れる。3点が揃った時点で arXiv:2603.04370 を bib に追加する。

## 2. 適応攻撃(AutoDojo)に対する gateway の頑健性評価

- **状態**: 候補。現行計画の評価は AgentDojo の固定攻撃(`eval/agentdojo_live_injection.py`)。
- **参照**: `paper/AutoDojo/README.md`(bib キー `ma2026autodojo`、追加済み)。
- **概要**: AutoDojo は固定テンプレート攻撃で 0% に見える防御でも適応攻撃で全体
  28%・行動が開いたタスクで 64% まで攻撃成功率が戻ると報告する。認可 gateway は
  文面の言い換えに依存しない構造的防御なので、適応攻撃への耐性はむしろ本設計の
  強みを示せる可能性が高い。
- **なぜ今やらないか**: 適応攻撃の実行は攻撃側 LLM の反復呼び出しを要し、評価費用
  が大きい。まず固定攻撃での主張範囲を固めるのが先。
- **着手の条件**: 査読者から「固定攻撃のみの評価」を突かれる会議に出す場合は、
  投稿前に最低限の適応攻撃試行(小さい問い合わせ予算での AutoDojo 実行)を足す。

## 3. τ³-bench(release 固定)でのゲート込み可用性再測定

- **状態**: 候補。現行の可用性測定は自前タスク群(AVAIL_4 系)。
- **参照**: `paper/Tau3Bench/README.md`(bib キー `sierra2026tau3bench`、追加済み)、
  `paper/Tau2Bench/README.md`(`barres2025tau2bench`)。
- **概要**: 外部の標準ベンチで「gateway を挟んでも可用性が保たれる」ことを示せる
  と、自前タスク群のみの主張より説得力が増す。使うなら旧 τ-bench ではなく
  τ³-bench の airline / retail 修正版を release タグ固定で。再測定は常に
  ゲート込み(確認関門で人が答える形式)で行う — ゲート無し測定は行わない。
- **なぜ今やらないか**: dual-control やユーザーシミュレータとの統合は gateway の
  連携層に新規実装を要する。また τ 系は採点変更が続いており(上記 v1.0.1)、
  測定時期の固定と再現手順の記録が前提になる。
- **着手の条件**: 連携層の実装工数を見積もった上で、対象を airline / retail の
  2ドメインに限定して開始する。banking_knowledge は候補1と同じ理由で除外。

更新規則: 候補の追加・状態変更時は本書を直接編集し、判断日を残す。採用した候補は
「状態」を「採用(YYYY-MM-DD)」に変え、`paper/` への追加を同時に行う。
