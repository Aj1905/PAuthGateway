# Ingress 設計: まず SDK 直結、傍受は後から

本書は、**SDK / 直接統合を最初の ingress(橋頭堡)** として扱い、**傍受型 ingress(プロキシ / フック)は同じ契約の背後の差し込み口として**後で作る、という決定を記録する。

本書は `DESIGN_STATUS.md` の規律に従う。確定した決定と未解決の問いを分離し、設計が実際以上に固まって見えないようにする。

相互参照: `ARCHITECTURE.md` §1.1/§1.2(そこでは「ingress」を*アダプタ*の水準で使う。二水準の定義は `GLOSSARY.md` の「ingress の二水準」を正とする。アダプタの実装状態の正は同書 §1.1 の結合境界表である)、`DESIGN_STATUS.md` のボトルネック #2(プロンプト捕捉が製品上の主たるリスク)。

## 核心原理: ingress の方式はエージェントを誰が所有するかで決まる

| エージェントの所有者 | Ingress の方式 | 理由 |
|---|---|---|
| 顧客が自作(自社内エージェント) | **SDK / 直接統合** | コードは顧客のものなので、ゲートウェイ(pauth の核)を直接呼べる。傍受は不要。 |
| サードパーティ製(無改変の Claude Code、Codex、…) | **傍受**(推論プロキシ / フック) | コードを変更できないため、プロンプトと tool の事象を外側から捕捉しなければならない。 |

どちらの ingress 方式も**同じ** `PromptMessage` / `ToolCallMessage` 契約(`gateway/ingress/agent_channel.py`)へ正規化され、**同じ**決定的な核(`pauth/`)へ流れ込む。異なるのは ingress アダプタだけである。これはまさに、`ARCHITECTURE.md` の疎結合な境界が想定していた使い方である。

ただし注意: **本書は「ingress」を二つの水準で使う** — *アダプタ*(上記の SDK か傍受か。`ARCHITECTURE.md` の "ingress" はこの水準のみ)と、方向モデルの*区間(leg)*である(二水準の定義は `GLOSSARY.md` の「ingress の二水準」)。捕捉と強制は往復の**同じ leg には載らない**。Mode 2 を読む前に、下の「方向モデル」を読むこと。

## 方向モデル: 「ingress」≠ 単一の方向(request/response × ingress/egress)

エージェント↔プロバイダのやり取りは**往復**であるため、ゲートウェイから見ると leg は一つではなく四つある。これらを混同すると、ゲートウェイが*観測*できるのは一部の leg だけであり、*強制*できるのも別の leg だけである、という事実が見えなくなる。

```text
          request-ingress          request-egress
agent ──────────────────▶ gateway ──────────────────▶ provider
      ◀──────────────────         ◀──────────────────
          response-egress         response-ingress
```

| Leg | 配線上の方向 | 流れるもの | ゲートウェイの役割 |
|---|---|---|---|
| **request-ingress** | agent → gateway | ユーザープロンプト(リクエスト入) | プロンプトを**観測** → `PromptMessage`。一度だけ計画(A1–A3) |
| **request-egress** | gateway → provider | ユーザープロンプト(リクエスト出) | 中継。必要に応じ送信前にプロンプトを伏せ字化してもよい |
| **response-ingress** | provider → gateway | モデルの `tool_use`(レスポンス入) | tool 呼び出しを**観測** → `ToolCallMessage` |
| **response-egress** | gateway → agent | レスポンス(レスポンス出) | **強制** — 拒否された `tool_use` を、エージェントが目にする前に書き換え/遮断(B1–B4) |

ここから直ちに二つの帰結が導かれる。

1. **観測は ingress の leg に宿り、強制は response-egress に宿る。** プロンプトの捕捉(request-ingress)と tool 呼び出しの捕捉(response-ingress)は読み取り専用のタップである。tool 呼び出しを実際に*止める*には、読み書き可能なタップである **response-egress** の上で動かなければならない。これが「捕捉は強制ではない」(下の Mode 2)の配線水準での言い換えである。
2. **二つの契約は二つの ingress leg に対応する。** `PromptMessage` = request-ingress、`ToolCallMessage` = response-ingress。核が egress に直接触れることはなく、**response-egress** の leg が適用すべき判定を返すだけである。

**tool 実行チャネル**(agent ↔ MCP / 外部 tool)は、それ自体の四つの leg を持つ*第二の*往復である。tool プロキシ(下記 B)は推論の往復ではなく、**その往復のリクエスト leg**(agent → tool のリクエスト)の上で動く。

各方式がこれらの leg をどう占めるか:

| | request-ingress | request-egress | response-ingress | response-egress |
|---|---|---|---|---|
| **Mode 1 SDK** | `submit_user_prompt`(帯域外の呼び出し) | —(エージェント自身がプロバイダを呼ぶ) | `handle_tool_call`(帯域外の呼び出し) | 判定 = 関数の返り値。**エージェント自身のコードがそれを適用する** |
| **Mode 2 推論プロキシ** | プロキシがリクエストを読む | プロキシが中継する | プロキシがレスポンスを読む | プロキシが書き換え/遮断する — 経路 (A) |

**Mode 1 ではゲートウェイはインラインにいない。** エージェントの傍らに置かれた呼び出され先であり、ゲートウェイにとって request-egress は存在せず、「強制」は顧客のコードが従うことに同意している真偽値にすぎない。**Mode 2 ではゲートウェイはインラインにある**ため四つの leg がすべて実在し、**(壊れやすい)レスポンス書き換えは response-egress でしか行えない** — まさにそれこそが、エージェントの状態に不整合を起こしうる理由である。

## 決定事項

- **橋頭堡 = Mode 1(SDK / 直接)、自社内製エージェント / ToB 区分。** これを今作る。
- **Mode 2(傍受)は先送りする。** 同じ契約の背後に接続できるよう ingress 境界は開けたままにするが、**傍受アダプタはまだ実装しない。**
- **ToC は課金対象の区分ではない。** 消費者向けの購読課金・支払いの経路は提供しない。

構築の規律(三つの層。ひとまとめにしないこと):

| 層 | 今作るか | 補足 |
|---|---|---|
| 共有の核(`pauth/`、Enforcer、envelope、`AgentChannel` 契約) | **作る** | 両方式に仕える。土台である。 |
| Ingress 境界(安定した契約を持つきれいな継ぎ目) | **既に存在** | Mode 2 を後から接続できるよう、きれいなまま保つ。 |
| Mode 1 SDK ingress | **作る** | 橋頭堡。最初の顧客はこれを使う。 |
| Mode 2 傍受 ingress(プロキシ / フック) | **一部 — 核は実装済み** | 何がどこまで実装済みか(フック、`InterceptingProxy`、egress lockdown、TLS/ネットワーク外殻)は `ARCHITECTURE.md` §1.1 の結合境界表と §2 を正とする。 |

「両方作る」とは両方を*準備する*(共有の核 + 開いた境界)ことであって、両方を*実装する*ことではない。Mode 1 の検証前に Mode 2 のアダプタを書くのは、未検証の第二の用途に対する早すぎる抽象化である。

## Mode 1 — SDK / 直接統合(橋頭堡。今作る)

顧客自身のエージェントコードがゲートウェイを直接呼ぶ。素のプロンプトを一度だけ提出し、以後は各 tool 呼び出しを実行前に Enforcer に通す。

```text
customer agent code
   ├─ submit_user_prompt(prompt)        → plan once   (pauth A1→A2→A3)
   └─ on each tool call:
        handle_tool_call(tool, args)     → enforce     (pauth B1–B4)
        → allowed → execute → record envelope (B4)
        → denied  → refuse
```

これが(単なる一案ではなく)橋頭堡である理由:

1. **最も難しい未解決問題を消し去る。** `DESIGN_STATUS.md` のボトルネック #2(無改変のエージェントから素のプロンプトを頑健に捕捉すること)は、ここには**存在しない** — 顧客が素のプロンプトと tool 呼び出しを SDK に直接手渡すからである。base-URL の MITM も、フックの除去も、TLS ピン留めも、利用規約のグレーゾーンもない。
2. **プロバイダに支配された接点という戦略上のリスクを消し去る。** 統合点はプロバイダのフック面ではなく、顧客自身のコードである。プロバイダの思惑によって劣化させられることがない。
3. **証明可能な L3 の製品を今すぐ出荷できる。** 完全な捕捉 + 完全な強制を、壊れやすさなしに、傍受技術の成熟を待たずに実現できる。

市場の実情(取り繕わないこと):

- **より狭い区分。** 大半の企業は既製のエージェントを使う。自前でエージェントを作り、*かつ*第三者の認可フレームワークを求める層はより小さい。しかしその層はより洗練されており、価値が高く、一度統合されれば離れにくい。「狭く守りやすい楔」戦略に適合する。
- **競争はより激しい。** 「自分のエージェントを守る」領域は、無改変エージェント向けファイアウォールの領域よりも直接の競合が多い(NeMo Guardrails、Guardrails AI、Llama Guard、各エージェントフレームワーク)。差別化は、場当たり的・確率的な検査に対する**決定的で証明可能なタスク限定**に強く依拠しなければならない。
- **フレームワーク対自作の緊張。** 自前でエージェントを作れるチームは、自前の検査も手書きできる。PAuth は自家製の解より明確に優れていなければならない。すなわち、原理に基づき、envelope に裏打ちされ、一度だけ計画する認可フレームワークであり、正直な FP/FN の数字で証明されたものであること。

## Mode 2 — 傍受(無改変エージェント。先送り、差し込み口のみ)

コードを変更できないエージェント(Claude Code、Codex)向け。**完成したアダプタとしてはまだ提供していない**(部分実装の現状は `ARCHITECTURE.md` §1.1 の結合境界表を正とする)。境界を後付けではなく設計に織り込んだまま保つため、ここに記録する。

傍受の下位方式は、エージェントの認証方法に依存する。

| エージェントの認証 | 傍受 | 補足 |
|---|---|---|
| API キー / API(Bedrock / Vertex / Azure) | **推論プロキシ**(base-URL の付け替え、プロバイダへ中継) | MITM に後ろ暗さはない。鍵は顧客のもの。API の利用規約は API 上に構築することを許している。ToB に自然に適合する。 |
| 購読(OAuth、席単位課金) | **フック**(`UserPromptSubmit` + `PreToolUse`) | 推論プロキシは塞がれている。トークンはファーストパーティに紐づき、TLS ピン留めの可能性があり、利用規約上のリスクがある。フックはエージェントのランタイム内で動き、認証方法に依存しない。 |

購読の壁(そこで推論プロキシが成り立たない理由):

1. OAuth トークンはプロバイダのファーストパーティ利用のために発行される。第三者のプロキシを通した中継は、利用規約 /「意図されない利用」に違反する可能性が高い。
2. TLS ピン留めがあれば、ローカルネットワークでの MITM は無力化される。(現行の Claude Code については未検証 — 実機での確認が必要。)
3. 信頼を売る製品が、利用規約違反の MITM を出荷してはならない。「購読は未対応。API / Team / Enterprise のみ」と明示するほうが望ましい。

捕捉は強制ではない(推論プロキシ経路に当てはまる)— これは request/response 分離の具体形である。

- 推論プロキシは、モデルが発する tool 呼び出しを **response-ingress** で**観測**する。それだけでは tool 呼び出しを**遮断**できない。遮断するには **response-egress** の上で動かなければならない。
- **(A) レスポンス書き換え**(推論チャネルの **response-egress** で動く)— 拒否された `tool_use` を、エージェントに届く前にモデルのレスポンス内で書き換える。エージェントの外に出ることのない内部 tool(Claude Code の `Bash`、ファイル操作)を gate できる — ボトルネック #5(バイパスとサイドチャネル)の抜け道に触れられる唯一の無改変手段である。壊れやすい。飛んでいる途中のレスポンスを書き換えると、エージェントの状態に不整合を起こしうる。
- **(B) tool プロキシ**(推論の往復ではなく、**tool 実行チャネルのリクエスト leg** で動く)— MCP / 外部 tool の呼び出しをゲートウェイ経由に経路付けし、そこで拒否する(`gateway/providers/mcp_suite.py`)。頑健だが、エージェントの内部 tool はここを通らない。
- 完全な L3 の傍受 = (A) + (B) — 両者は**異なるチャネルの異なる leg** を受け持つため、どちらか一方だけでは完全にならない。

中継が実現可能であることを示す先行例(新規性はない): LiteLLM、Cloudflare AI Gateway、Helicone、OpenRouter。新規なのは、その中継の上に PAuth を載せることである。

## 未解決の問い(未決定)

1. **Mode 1 SDK の形。** SDK の表面はどうあるべきか。最小形: 既存の `Gateway` クラスを包む `submit_user_prompt` + `handle_tool_call`。言語束縛(まず Python。他は後か?)。同期か非同期か。エラー/拒否の返り値契約。
2. **Mode 1 の差別化の証明。** タスク限定において PAuth が自家製の検査や確率的ガードレールに勝ることを示す、具体的なデモ + 正直なベンチマーク。これは単なるコードではなく、市場開拓上の唯一最重要の成果物である。
3. **Bash / 内部 tool の扱う範囲(Mode 2)。** (A) レスポンス書き換えでしか到達できない。未解決のボトルネック #5(バイパスとサイドチャネル)の決定と交差する。Mode 2 と一緒に先送りする。
4. **購読対応の方針。** おそらく「未対応。API / Team / Enterprise のみ」。Mode 2 の作業を始める前に確定させる。
5. **預かり(custody)。** 平文のプロンプト + 鍵を目にするあらゆる傍受経路は、信頼が確立するまで**自己ホスト限定**とする。

## 進め方の順序

1. 共有の核を作り、ingress 境界をきれいに保つ(ほぼ既存)。
2. **Mode 1 SDK ingress** と差別化のデモ/ベンチマークを作る。
3. 最初の自社内製エージェント(ToB)顧客を Mode 1 に載せる。
4. **Mode 1 の検証が済んだ後に限り**、Mode 2 の傍受を実装する。推論プロキシ + tool プロキシ(API/ToB)の経路から始める。利用規約上明確に問題のない仕組みが存在しない限り、購読は対象外として扱う。
5. 各アダプタがコードとして存在するようになった後に限り、`ARCHITECTURE.md` §1.1/§1.2 を実際の ingress に合わせて更新する。
