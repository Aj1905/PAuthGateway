## 実行済み：検証処理の不一致の調査

計画器の自己修復処理は、後段の `prepare()` と異なり、意味を保つコード整形
`normalize_run()` を適用せずに意味検証していた。そのため後段が受理できる
候補にも再生成を要求していた。

保存済みの AgentDojo 最終候補を全件比較した結果：

| 項目 | 候補数 |
|---|---:|
| 調査した最終候補 | 6,014 |
| 従来の自己修復処理で DSL 棄却 | 1,262 |
| 後段の受理処理で DSL 棄却 | 1,258 |
| 整形により受理可能になる候補 | 4 |
| 自己修復処理だけ受理し、後段で DSL 棄却 | 0 |

この差は小さい。保存済み最終候補には修復途中で捨てた案が含まれないため、
不要な再生成全体の頻度も分からない。独立タスク6,014件の評価ではなく、
複数設定の候補6,014件の診断である。タスク完了率や最小権限の改善値には換算しない。
救済された4候補は認可付きの模擬実行でいずれもクラッシュ・拒否なしだった
（認可済みツール呼び出し数は順に7・2・2・3）。これはタスク完了判定ではない。

`gateway/planning/agentic_planner.py` で、後段と同じ順序で整形してから意味検証する
よう修正した。精査と意味判定には元のコードを渡し、禁止ツールの精査を継続する。
コード整形で救済できる二つの入力について、再生成が不要になることと、認可付き実行
で期待する結果が得られることを確認した。禁止ツールと未対応のツール呼び出しを含む
リスト内包の拒否も確認した。

関連テスト70件が合格し、`git diff --check` も合格した。

## 認証後の比較実験

優先順を次のように固定する。各介入は既定プロンプトへ即時採用せず、独立した条件
として比較する。Claude には失敗分析と条件外の操作の見落としの批評を依頼する。

1. **条件と訂正を保持する指示。** 操作ごとの対象、数量、条件、禁止事項を
   生成前に整理させる。同じ入力内の明示的訂正は最終指示を採用し、訂正前の操作を
   併記して許可しない。条件が不成立の時に操作しないことも計画へ残す。
2. **結果の型に合わせた選択指示。** 検索結果が文章か、一覧か、単一の対象かを
   ツールスキーマから区別し、存在しない項目や一覧を捏造しない。該当なし・複数該当
   の時の扱いを、利用者の依頼に従って記述する。
3. **修復中の条件と手順の保持。** DSL 棄却を修正する際、元の依頼の条件や
   必要な操作を削って受理率だけを上げない。表現できない依頼は失敗として記録し、
   空計画を成功に数えない。既存の実行時試行が空計画を増やした結果も再発確認する。

開発用入力と最終評価用入力を生成前に分割する。同じ意味の言い換えは同じ分割へ
入れ、対象名・値・ツール群を変えた入力も含める。各条件は同じモデル・予算で
最低3回生成し、プロンプト・モデル・ツールスキーマ・実装のハッシュで結果を分離する。
最終評価の結果を見た後の追加調整には、別の未使用入力を用意する。

既存 AgentDojo の `GT_NO_MISSING_CALLS`、`GT_NO_EXCESS_CALLS`、
`GT_EXACT_AUTHORIZATION` と `OUTCOME_TASK_COMPLETED` を分けて報告する。
新しい入力では条件成立・不成立、境界値、該当なし、複数該当を含む環境を用意し、
正しい操作が認可されることと、対象・数量・条件を変えた操作が拒否されることを
対で確認する。有限の事例の検査を、権限空間全体の最小性証明とは呼ばない。

採用条件は、タスク完了と必要な操作の網羅が改善し、条件外の操作の認可を増やさない
こと。受理率だけの上昇や、操作を減らしただけの過剰減少は採用理由にしない。
この比較実験は認証待ちであり、未実行である。
