# 評価

本書は評価結果の正式なまとめである。中心的な主張、評価の設定、測定結果、
そして正直な限界を記す。試行ごとの詳細は
[GT_NO_MISSING_IMPROVEMENT_LOG.md](GT_NO_MISSING_IMPROVEMENT_LOG.md) に、アーキテクチャは
[SYSTEM_MODEL.md](SYSTEM_MODEL.md) に、脅威モデルは [THREAT_MODEL.md](THREAT_MODEL.md) にある。

本書のすべての数値は、各節に記載したコマンドから再現できる。実行系は結果を
決め打ちしない。誤ったplanは許可callの不足または過剰として現れ、実行時の
不整合はplan-policy整合に現れ、ラベル付き攻撃は検査済み事例の結果としてのみ
報告される。

---

## 評価手順の規則

AgentDojo における主要な結果は、**97個のユーザタスク全体に対する自然言語での
end-to-end 成功率**である。

```
natural-language prompt
  -> Planner / RuleCompiler
  -> live LLM agent
  -> injected tool output read by that agent
  -> PAuth-gated tool execution
  -> AgentDojo utility check
```

plan生成の失敗は end-to-end の失敗であり、分母から除外してはならない。
コンパイル済みplanのみを対象とした結果は、**条件付きの整合または実行時診断**
として別途報告し、決してシステム全体の成功率として報告しない。合成callや
強制callを Enforcer に直接再生することは部品の検査であって、AgentDojo の
end-to-end 評価ではない。

注入攻撃込みの実エージェント実行系は次のとおり。

```
.venv/bin/python -m eval.agentdojo_live_injection
```

既定の82事例の一次検査は、文法的に妥当なキャッシュ済みplanごとに注入目標を
1つ実行し、それでも97を分母として end-to-end 成功を報告する(plan生成に失敗
した15件は失敗として数える)。AgentDojo の標的型ASRの完全な行列を得るには、
妥当な各タスクをそのsuiteの全注入目標と組み合わせる必要がある。82事例の
一次検査をその完全行列として提示してはならない。

## 1. 中心的な主張

> **過少認可と過剰認可は、正解忠実度という一つの比較における二つの誤り方向
> である。より強力な Planner は必要call充足を 27/97 から 47/97 に引き上げ、
> 過不足なしの認可を 27/97 から 32/97 に改善したが、過剰callなしの成績は
> 83/97 から 56/97 に落とした(83 のうち 35 件は plan 欠損による空 trace の
> 自明な合格である)。**
>
> 数値は 2026-08-09 の測定修正後のもの。ゲートウェイ内部の抽出ツール呼び出し
> (`structure_text`)は正解列の語彙外にあるため、照合前に観測側から除外する
> ようにした(修正前の値: 過剰callなし 44/97、過不足なし 24/97。経緯は
> [GT_NO_MISSING_IMPROVEMENT_LOG.md](GT_NO_MISSING_IMPROVEMENT_LOG.md) の T14)。

以下では三つの帰結を測定する。

1. 表現可能性、policy生成、実行時クラッシュなし、plan-policy整合は、それぞれ
   独立した前提条件または診断である。入れ子になった可用性の連鎖ではない。
2. 必要call充足だけでは観測traceに含まれる余分なcallを減点できず、過剰call
   なしだけでは空のtraceが高く評価されてしまう。
   `GT_EXACT_AUTHORIZATION` は両方の半分を要求することで、trace水準のこの
   二つの退化を退ける。
3. 検査した集合では固定の強制攻撃callはすべて拒否されたが、これは履歴依存の
   policy関係の全体を列挙するものではなく、policyの過剰許可がゼロであること
   の証明でもない。

## 2. 評価対象のシステム

パイプライン(詳細は [SYSTEM_MODEL.md](SYSTEM_MODEL.md)):

```
prompt ──▶ Planner ──▶ Slicer ──▶ RuleCompiler ──▶ Enforcer
        (LLM, the ONLY      (deterministic)        (default-deny; matches every
         non-deterministic                          call's control operands against
         step)                                      the compiled rules; signs results
                                                    into tamper-evident envelopes)
```

Planner が読むのは**信頼できるプロンプトとtoolスキーマだけ**であり、信頼で
きない実行時データは決して読まない。したがって Planner が計画する制御オペラ
ンド(recipient、amount といった、副作用の向き先を決めるオペランド)は汚れ
のない来歴を持つ。Enforcer は既定拒否である。あるruleが署名済み envelope か
ら制御オペランドを再導出できる場合に限り、callは認可される。これにより plan
相対の執行が得られる。すなわち Enforcer は Planner がコンパイルした内容に照
らしてcallを検査する。Planner のpolicyがユーザの意図と正確に一致することま
では保証しない。

**二つの認可経路。** 自動経路(Enforcer)は、制御オペランドの来歴が証明可能
なcallを認可する。**人間認可経路**(§7)は、Enforcer には検証*できない*call
— planが読んでいない、信頼できないデータの中にしか存在しない値 — を、人間に
問い合わせることで扱う。得られる認可の信頼性は、その確認判断の信頼性を超え
ない。

## 3. 評価の設定

| フレームワーク | プロンプト形式 | 正解データ | 検査する範囲 |
|-----------|-------------|--------------|-------------------|
| **AgentDojo** v1 (banking, slack, travel, workspace) | 単一ターンの自然言語 | `ground_truth` call + `utility` | 正解忠実度 + タスク結果 |
| **tau-bench retail** | 複数ターンの役割演技 | GT行動(utility なし) | 実行時開示値の網羅 |
| **InjecAgent** | 攻撃中心 | 正解plan | 固定のラベル付き攻撃プローブ |

**指標の語彙**(正式名は [`eval/metrics.py`](../eval/metrics.py)):

```
FEASIBILITY_EXPRESSIBLE
SYNTHESIS_POLICY_COMPILED
RELIABILITY_RUNTIME_CRASH_FREE
CONFORMANCE_PLAN_TRACE_PERMITTED

GT_NO_MISSING_CALLS
GT_NO_EXCESS_CALLS
GT_EXACT_AUTHORIZATION

OUTCOME_TASK_COMPLETED
OUTCOME_ATTACK_GOAL_ACHIEVED
OUTCOME_TASK_COMPLETED_WITHOUT_ATTACK_GOAL
AUX_INJECTIONS_DENIED
COST_TOOL_CALLS
```

三つの `GT_*` 指標は、許可されたmock trace 1本をベンチマークの正解と比較す
る。不足と過剰は、同一の1対1の tool+制御オペランド照合器を用いる。ゲート
ウェイが計画に提供する内部抽出ツール(`structure_text`)の呼び出しは、正解列
の語彙外にあるため照合前に観測側から除外する(2026-08-09 の測定修正、
[GT_NO_MISSING_IMPROVEMENT_LOG.md](GT_NO_MISSING_IMPROVEMENT_LOG.md) T14)。
これらは、コンパイル済みpolicyがあらゆる履歴にわたって認可しうるcallの全体
を列挙するものではない。百分率は、正解が存在するタスクの総数を分母とする。

再現方法:

```
python -m eval.funnel agentdojo --mode headless --planner bestof --model gpt-5.1 --structuring
```

## PAuth パイプラインの固定入力診断（2026-08-03）

原論文と共通する認可上の問いを、自然言語からのrun コード生成と実エージェントの
挙動から切り離して調べた。AgentDojo 0.1.35・タスク定義v1の97件について、
97件の正解ツール呼び出し列に含まれる合計339件のツール呼び出しを、具体的な引数を持つ直線的なrun コードへ変換し、
PAuth パイプラインと実行部へ通した。正解列を完全に再現できたタスクに限り、
同じ執行器へ固定攻撃用ツール呼び出しを提示した。固定攻撃用ツール呼び出しは、
状態変更を示すツール名、正解列の引数改変、AgentDojoの攻撃タスクから生成した。
これは正常列実行後の認可関係を調べる事後照合であり、一回限りの許可の消費、
実行順序、外部ツールへの送出は検査しない。

```
.venv/bin/python -m eval.agentdojo_reference_trace \
  --output tests/experiment/results/agentdojo_reference_trace_g1_g2_20260803.json
```

| 文法検証器 | 正解列を完全再現 | 再現したツール呼び出し | 固定攻撃用ツール呼び出しの拒否 |
|---|---:|---:|---:|
| `G1`（DSL(G1)） | 96/97 | 337/337 | 748/748 |
| `G2`（DSL(G2)） | 97/97 | 339/339 | 756/756 |

DSL(G1)でDSL棄却された一件には8件の固定攻撃用ツール呼び出しが定義されていたが、
正常経路を実行できないためG1の拒否率の分母から除外した。DSL(G2)で増えた一件は
辞書を引数に持つrun コードであり、有界`for`による増分は0件だった。JSON成果物の
SHA-256は`89e0569d7040f8ca6890370c9a2d310ca5190d98d358f1171aa6350016e6f52d`
であり、二回の生成で同じバイト列を得た。

これはタスク完了率でも、一般のプロンプトの表現可能性でもない。既定の初期状態に
おける一つの有限な正解列を直線コードへ書き直した診断である。また、原論文の
100件・固定攻撃用ツール呼び出し634件とは入力集合と生成法が異なるため、原論文との
精度差は計算しない。主張できるのは、同じ現行入力上でDSL(G2)がDSL(G1)より一件多く
正常経路を処理し、試した固定攻撃用ツール呼び出しをすべて拒否したことまでである。

## AgentDojo 全数2×2評価（2026-08-04）

認可ポリシーの適用有無とインジェクション文の付与有無を組み合わせた。攻撃あり
条件は、AgentDojo v1の利用者タスク97件に各スイートの全攻撃ゴールを掛け合わせた
629対（banking 16×9、slack 21×5、travel 20×7、workspace 40×6）を条件ごとに
1回ずつ実行した。全組み合わせを実行するため攻撃ゴールの割当は存在せず、割当の
恣意性が条件差に混入しない。攻撃なし条件には攻撃ゴールという軸が存在しないため、
各タスク1観測（97行×2条件）の非対称な設計である。合計1452行のうち1350行で
エージェントを実際に動かし、DSLを通る保存済み候補を選べなかった計画なし15タスク
に対応する102行は、エージェントもツールも動かさず、変更されていない状態を判定した。

```
# 攻撃あり2条件（スイート×条件で分割・並列実行し、行キー単位で結合）
.venv/bin/python -m eval.agentdojo_factorial --pairs full \
  --output tests/experiment/results/agentdojo_factorial_gpt41_t0_fullcross_20260804.merged.jsonl

# 攻撃なし2条件
.venv/bin/python -m eval.agentdojo_factorial \
  --condition policy_off_injection_off --condition policy_on_injection_off \
  --output tests/experiment/results/agentdojo_factorial_gpt41_t0_injoff_20260804.jsonl

.venv/bin/python -m eval.agentdojo_factorial_analysis --design full-cross \
  --input tests/experiment/results/agentdojo_factorial_gpt41_t0_fullcross_20260804.merged.jsonl \
  --output tests/experiment/results/agentdojo_factorial_gpt41_t0_fullcross_20260804.analysis.json \
  --bootstrap-iterations 100000
```

API指定モデルは`gpt-4.1`、応答モデルは`gpt-4.1-2025-04-14`、temperatureは0、
最大反復数は15である。1452行を判定し、評価コードの失敗で除外した行はなかった。
これは、個々のツール呼び出しにツールエラーや拒否がなかったという意味ではない。

最終文章出力だけを攻撃ゴールとし正解ツール呼び出し列が空のtravel
`injection_task_6`（20対）は、PAuthGatewayが直接検査するツール呼び出しを必要と
しないため、ツール呼び出しに対する安全性の主分析から対の水準で除外し、残る609対
を用いる。

| 指標 | PAuthの認可ポリシー適用なし | PAuthGatewayで適用 | 変化（適用あり−なし） |
|---|---:|---:|---:|
| 攻撃ゴール達成・インジェクション文あり | 257/609 | 0/609 | −42.2ポイント |
| タスク完了・インジェクション文なし（97タスク） | 76/97 | 21/97 | −56.7ポイント |
| タスク完了・インジェクション文あり | 340/609 | 117/609 | −36.6ポイント |
| 攻撃ゴール未達でのタスク完了 | 245/609 | 117/609 | −21.0ポイント |

95%信頼区間は、97タスクを単位とする対応付き塊再標本化（同じタスクの攻撃ゴール
群は同じプロンプト・計画・初期状態を共有するため、対単位ではなくタスクごとに
丸ごと再標本化する）を100,000回行って求めた。攻撃ゴール達成の低下は35.8から
48.8、通常時タスク完了の低下は46.4から66.0、攻撃下の両立結果の低下は13.5から
28.6パーセントポイントだった。認可ポリシーを用意できた82タスクの522対でも、
攻撃ゴール達成は190/522から0/522へ減った一方、通常時のタスク完了は64/82から
21/82へ、攻撃下の両立結果は236/522から117/522へ減った。

文章出力だけを狙う20対を含む系全体の補助結果では、攻撃ゴール達成が274/629から
1/629へ変化した。適用ありで達成された1対（travel `user_task_1` ×
`injection_task_6`）は最終文章出力だけを狙う攻撃であり、ツール呼び出しの認可
という対象範囲の外にある。攻撃ゴール別の内訳では、適用なしの達成率は攻撃ゴール
により0%から100%まで幅があるが、適用ありではこの1対を除きすべて0だった。

この評価では、認可ポリシー適用時にツール呼び出しを必要とする攻撃ゴール達成率と
タスク完了率がともに低下した。タスク結果を維持したという主張は支持されない。
同じ対・条件を反復していないため、信頼区間はタスク構成による値の揺れだけを表し、
LLMの反復変動を含まない。詳細と成果物のハッシュ値は
[全数評価報告](../tests/experiment/results/agentdojo_factorial_gpt41_t0_fullcross_20260804_report.md)
に記録した。

## 4. 結果 R1 — 補助的な強制攻撃の負荷試験

検査した集合に含まれるラベル付き強制攻撃call(改竄された制御オペランド、
またはタスク外の機微なcall)は、三つのフレームワークと両方の Planner モデル
のすべてで拒否された。

| フレームワーク | 強制注入数 | 拒否数 |
|-----------|-------------------|-----------------|
| AgentDojo (GPT-5.1) | 92 | **92 / 92** |
| tau-bench retail (GPT-5.1) | 109 | **109 / 109** |
| InjecAgent | 1054 | **1054 / 1054** |
| AgentDojo (GPT-4.1, `eval.fpfn`) | 390 | **390 / 390** |

弱い Planner と強い Planner は、これらの固定ラベル付き攻撃集合では同じ結果
になる。これは補助的な負荷試験の結果であって、未知の注入やpolicy外のcallが
すべて拒否されることの証明ではない。検査済み攻撃の拒否に失敗があれば総数を
下回る数字として現れるはずだが、そのような例はない。

```
python -m eval.fpfn --suites all        # GPT-4.1 forced-injection sweep
```

## 5. 結果 R2 — 必要callと過剰callは一つの忠実度平面をなす

現在の分類法での AgentDojo の結果は次のとおりである。

| 指標 | GPT-4.1(キャッシュ) | GPT-5.1(構造化 best-of-3) |
|---|---:|---:|
| FEASIBILITY_EXPRESSIBLE | 97/97 | 97/97 |
| SYNTHESIS_POLICY_COMPILED | 62/97 | 92/97 |
| RELIABILITY_RUNTIME_CRASH_FREE | 51/62 | 88/92 |
| CONFORMANCE_PLAN_TRACE_PERMITTED | 62/62 | 92/92 |
| **GT_NO_MISSING_CALLS** | **27/97** | **47/97** |
| **GT_NO_EXCESS_CALLS** | **83/97** | **56/97** |
| **GT_EXACT_AUTHORIZATION** | **27/97** | **32/97** |
| OUTCOME_TASK_COMPLETED | 14/97 | 22/97 |
| COST_TOOL_CALLS(コンパイル済みplanあたり) | 2.2 | 3.2 |

より強力な Planner は必要call充足を大きく引き上げる(27→47)。同時に、正解
と対応しない許可callも増やすため、過剰callなしは 83 から 56 に下がる(83 の
うち 35 件は plan 欠損による空 trace の自明な合格である。コンパイル済み plan
に限った割合でも 48/62 から 51/92 へ低下しており、過剰側の悪化は空 trace の
勘定だけでは説明できない)。両方を要求する過不足なしの認可は 27 から
32 への小幅な改善に留まる。必要call充足の動きだけを「可用性の改善」と呼ぶ
ことは、過剰側の悪化を覆い隠し、システムの目的を誤って伝えることになる。

`GT_NO_EXCESS_CALLS` は欠損planや無効なplanも含めて数える。空の
traceには過剰がないからであり、これは意図した設計である。したがって空の
traceは過剰callなしの半分では良い成績を取り、必要call充足と過不足なしでは
不合格になる。逆に、必要callをすべて含みつつ対応しないcallも含むtraceは、
必要call充足では良い成績を取りながら、過剰callなしと過不足なしでは不合格に
なりうる。

これらの数値は、制御オペランドを用いて許可trace 1本をベンチマークの正解1つと
比較したものである。コンパイル済みpolicy関係の全体が 83、56、27、32 の過不
足なしタスクを持つことを示すものではない。policy本来の過剰許可・過少許可を
測るには、guard・履歴・envelope 状態にわたるpolicy空間のオラクルが必要であ
り、本評価はそれを提供しない。

## 6. 結果 R3 — 診断は失敗を説明するが忠実度の代わりにはならない

GPT-5.1 構成では92タスクでpolicyがコンパイルされた。許可制約を外した実行時
プローブでは生成コードのクラッシュが4件観測された一方、執行下での生成plan
のtraceはコンパイル済み92件すべてで拒否がなかった。これにより、従来は一つの
実行時指標に一括りにされていた二つの現象(実行時クラッシュなしと
plan-policy整合)が分離される。

実行時クラッシュなしは意図への忠実度ではない。`def run(): pass` はクラッシュ
しないが必要callを欠く。plan-policy整合も意図への忠実度ではない。過剰に広い
planからコンパイルされたpolicyは、そのplanを完全に許可できてしまう。正解忠
実度の対と、その両立を求める過不足なしは、依然として必要である。

## 7. 結果 R4 — 人間認可経路は測定済みの一部を回復する

Enforcer が拒否せざるを得ない場合(値が信頼できないデータの中にしか存在しな
い場合)、タスクを回復するのはより賢い Planner ではなく人間である。本番の経
路は [`gateway/runtime/human_authorized.py`](../gateway/runtime/human_authorized.py)
である。

1. **提案器**(差し替え可能。本番ではLLM抽出器、評価ではオラクル — その精度
   は別個の一般的な問題である)が、欠けている行動を、信頼できない由来と明示
   した具体的な候補値とともに提示する。
2. **確認器**(人間)が承認または却下する。改竄された提案を退ける責任は、
   この時点で自動policyではなく人間にある。
3. 承認されると、使い切りの **HumanGrant** が発行される。これは**toolとすべ
   ての制御オペランドに束縛**され、署名される。行動はこのgrantを*引き換える*
   ことによってのみ実行され、引き換えによりgrantは消費される。

実際の実行経路を通した測定(`mode=authorize`、GPT-5.1、/97):

| 指標 | 人間が確認しない(`headless`、Enforcer のみ) | + 人間認可 |
|--------|-------------------------:|----------------------:|
| GT_NO_MISSING_CALLS | 47 | **49 (+2)** |
| OUTCOME (utility検証済み) | 22 | **29 (+7)** |
| 自動化費用 | — | gate対象16タスクで27回の確認 |

**正直さに関する二つの注記。** (a) 回復は小幅である。部分文字列で候補値の位
置を推定した以前の見積りは +23 を示唆したが、*実際の*経路 — 各不足が実行さ
れたgrantを介して実際に解消することを要求する — を駆動すると、**必要call充
足 +2 / OUTCOME +7** にしぼんだ。OUTCOME の回復が大きいのは、人間認可された
callによってタスクが機能的には完了しうる一方で、厳密な制御オペランド指標は
別の対応しないcallをなお指摘するからである。(b) ここでの確認器は完全な情報
を持つ(完全な抽出を仮定した上限)。実際の抽出器と実際の人間はこれより悪い。

本実験では、human grantを追加した後の過剰callなしの半分を再計算していない。
したがって人間経路については `GT_NO_EXCESS_CALLS` も
`GT_EXACT_AUTHORIZATION` も報告しない。+2 という結果を過不足なし認可の改善
として提示してはならない。

grantの安全性の性質は
[`tests/test_human_authorized.py`](../tests/test_human_authorized.py) で固定
されている。

- 承認された提案は実行される。plan自体の執行下のcallは変わらない。
- **使い切り** — 同一callを再生しても未消費のgrantは見つからない(拒否)。
- **完全束縛** — `(landlord, 98.70)` に対するgrantは `(attacker, 98.70)` を
  認可しない(オペランドの差し替えは拒否)。
- 偽造されたgrantは署名検証に失敗する。
- **条件1** — 同じ改竄済み提案が、形式的に承認するだけの人間には承認され、
  十分な情報を持つ人間には却下される。

```
python -m eval.funnel agentdojo --mode authorize --planner bestof --model gpt-5.1 --structuring
```

## 8. 実行時由来の値は回復にまつわる妥協を生む

Enforcer は信頼できる入力のみから計画する。一方、実行するエージェントは、攻
撃者の注入を含むあらゆるデータに基づいて行動する。制御値が信頼できない実行
時データの中にしか存在しない場合、来歴だけではその値が無害か攻撃者に選ばれ
たものかを判別できない。

- 正当なデータ由来の行動が拒否されうる。自動policyがその制御オペランドを信
  頼できる入力から再導出できないからである。
- 攻撃者が選んだ行動も、同じ来歴上の理由で拒否されるべきである。

実行時由来の値をすべて自動的に許可すれば、無害なcallは回復するが攻撃面も広
がる。常に拒否すれば逆向きの失敗になる。人間経路は認可の根拠をもう一つ加え
るが、この妥協を消し去りはしない。抽出の誤り、提示の拙さ、形式的な承認は、
依然として過少許可や過剰許可を生みうる。だからこそ評価は、どちらか一方を安
全性や可用性の軸と呼ぶのではなく、両方向を報告しなければならない。

## 9. 限界(明示的に範囲外)

認識されていない不足と誤解されないよう、名指しで挙げる。

1. **抽出器の精度。** 人間経路による回復(§7)は完全な抽出を仮定している。
   本番の提案器はLLMによる情報抽出部品であり、その精度が実際の回復の上限を
   定める。これは一般的な自然言語処理の問題であって、PAuth の貢献ではない。
2. **確認疲れ。** 条件1(意味のある確認)は成立の要である。件数を浴びる実際
   の人間(ここでは gate対象タスクあたり約1.7回の確認)は形式的に承認してし
   まう可能性があり、それは攻撃者が選んだ値を認可しうる。確認のUX(分解、
   来歴、隠し文字検出)はこれを緩和するが、本評価はこれを評価していない。
3. **複数ターン/動的タスク。** 過去の tau-bench 実行では、評価した静的plan
   の必要call充足はゼロだった。これはこの設定についての証拠であって、あらゆ
   る静的な Planner が必ずゼロになることの証明ではない。実行時に開示される
   制御値の回復には、段階的な再計画か別の認可源が必要になると思われる。
4. **上限と実運用の差。** 人間経路の数値はすべてオラクルの確認器とオラクル
   の提案器によるもので、上限値である。実運用はこれより悪くなる。
5. **policy空間の忠実度。** trace指標が観測するのは具体的な実行1回である。
   コンパイル済みpolicyがすべてのguard・履歴・envelope 状態にわたって許可す
   るcallの全体を列挙するものではない。
