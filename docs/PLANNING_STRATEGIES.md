# 計画戦略

ゲートウェイは、単一の prompt-to-code 手法に製品の命運を賭けてはならない。
PAuth の安定した境界は次のとおりである。

```text
user intent -> restricted imperative run() code -> pauth.prepare() -> rules
```

`pauth.prepare()` より前のすべては、差し替え可能な A1 戦略である。

## 戦略名

設定、JSON メッセージ、環境変数では、次の正準名を使用する。

| 名称 | 状態 | 意味 |
|---|---|---|
| `deterministic` | 実装済み | 既知のプロンプトパターンに対する正規表現認識器。 |
| `llm-freeform` | 実装済み | 文法修復と任意の判定器 (judge) を備えた汎用 LLM A1。 |
| `auto` | 実装済み | 認識器の高速経路。不一致時は `llm-freeform` にフォールバックする(既定のメイン ingress 戦略 S2。`hybrid` とも呼ばれる)。 |
| `sufficiency-tightness` | 実装済み | 網羅優先で生成した後、削除のみの機械的監査で引き締める二段 A1(`gateway/planning/sufficiency_tightness.py`)。 |
| `interactive-structuring` | 登録済み | コード生成前の明確化の対話ループ。 |
| `specialized-codegen` | 登録済み | 専用の命令型コードモデル+検証器による再試行。 |
| `formal-semantic` | 登録済み | 形式的な自然言語パーサ/意味解析の段階。 |

メイン ingress(`AgentChannel`)の既定値は `auto` である
(`PAUTH_PLANNER_STRATEGY` が未設定の場合)。`PAUTH_PLANNER_SUITE` がなければ、
`auto` にはフォールバック先がなく、受理集合は `deterministic` と同じになる。
`Gateway.submit_user_prompt` は `deterministic` を直接使用する。

実行時の選択:

```bash
PAUTH_PLANNER_STRATEGY=llm-freeform
PAUTH_PLANNER_SUITE=shopping
PAUTH_PLANNER_MODEL=gpt-4.1
PAUTH_PLANNER_MAX_RETRIES=3
```

登録済みだが未実装の戦略は、明確なメッセージとともに意図的に拒否される。
これらは戦略の枠であり、無言のフォールバックではない。

## 戦略 1: 対話的構造化

A1 生成の前に、誘導型の「Grill me」方式の対話を用いる。

流れ:

1. ユーザーの生の自然言語タスクから始める。
2. 欠けているオペランド、条件、ツール、日付、数量、宛先、曖昧さの解消に
   ついて、的を絞った質問をする。
3. 構造化されたタスクプロンプト、または構造化された意図オブジェクトを生成する。
4. その構造化表現をコード生成器に渡す。
5. 生成された命令型コードを `pauth.prepare()` で検証する。

これは、入力タスクの指定が不十分または曖昧な場合に有用である。モデルに値を
黙って捏造させるのではなく、欠けている意図を表面化させるため、製品開発の
初期段階にも適している。

厳格な制約: この戦略は、計画立案の前にユーザーとの対話面を必要とする。
ゲートウェイがユーザー向けのプロンプト段階を掌握していない限り、既に稼働中の
エージェントに対する「ネットワーク設定のみ」と同じにはならない。

失敗モード:

- エージェントファイアウォールを装った入力フォーム製品になりかねない。
- 質問が広すぎると、ユーザーは曖昧な回答をし、Planner は結局詳細を捏造する。
- 得られた構造化プロンプトが監査可能でなければ、この戦略は幻覚をコード生成
  からプロンプト書き換えへ移すだけである。

設計上の含意:

- 対話的な収集器は PAuth の中核の外に置く。
- その出力は、他と同じ Planner への入力の一つとして扱う。
- 生のプロンプト、質問、回答、最終的な構造化プロンプト、生成コード、
  検証結果を保存する。

## 戦略 2: 専用の命令型コードモデル

ユーザーのタスク+ツールスキーマから制限付き命令型 `run` コードを出力する
ことだけを役割とするモデルを、訓練または調整する。

流れ:

1. ユーザーのタスクと利用可能なツールスキーマを与える。
2. 専用モデルが `def run(...): ...` を出力する。
3. 決定的な検証器を実行する: 文法、意味検査、スライシング、ルールの
   コンパイル。
4. 検証に失敗した場合、検証器の正確なエラーをフィードバックして再試行する。
5. 再試行の予算を使い切ったら、タスクを拒否する。

これが機能すれば、ゲートウェイは手の込んだプロンプトテンプレート論理を
必要としない。複雑さは、モデルの訓練・評価と、小さな決定的修復ループに移る。

実行時の構成が単純なままであるため、この戦略には魅力がある。

- 生成呼び出しは一回;
- 検証器は一つ;
- 有限回の再試行;
- 失敗時は既定拒否 (default-deny)。

悩ましいのはデータである。十分な量の高品質な
`prompt + tool schema -> restricted run() code` の例がなければ、この戦略は
体裁のよいラベルの付いた希望的観測にすぎない。モデルは文法的な妥当性だけで
なく、意図の正確な捕捉についても評価しなければならない。

失敗モード:

- 文法的には妥当だが、ユーザーの意図を取りこぼすコード。
- よくあるベンチマークは満たすが、実際のユーザープロンプトでは失敗するコード。
- 玩具的なスイートに過剰適合し、実際の MCP ツールに転移しない訓練データ。

設計上の含意:

- 検証器のフィードバックはモデル非依存に保つ。
- 失敗した生成と検証器のエラーをすべて訓練データとして記録する。
- 文法成功の指標と、意図忠実性の指標を分離する。

## 戦略 3: 形式的な自然言語解析

自然言語プロンプトを形式化し、構文・意味解析を通じて翻訳することで、LLM の
役割を可能な限り最小化する。

候補となる形:

1. 受理するタスク言語を制限する。
2. プロンプトを形式文法で構文解析する。例えば範疇文法や、それに類する
   合成的意味解析器。
3. 解析された意味形式を、ツールの動作、オペランド、guard、データ依存関係へ
   写像する。
4. 制限付き命令型 `run` コードを出力する。
5. `pauth.prepare()` で検証する。

これは知的には最も整った方向だが、製品化からは最も遠い。受理するタスク言語
を意図的に狭めるか、製品が明示的な制限言語を許容できる場合にのみ、実用的に
なる。

失敗モード:

- 実際のユーザープロンプトが文法の範囲外に落ちる。
- 文法が、保守不能な例外の山に育つ。
- 手で選んだ例では網羅率が良く見えるが、本番の言語では崩壊する。
- 曖昧さの解消が、いつの間にかもう一つの隠れた LLM 的な部品になる。

設計上の含意:

- 既定の経路ではなく、研究用の枠として保持する。
- テンプレートと形式意味論が現実的な、狭く価値の高い領域に用いる。
- 拒否率を正しさとは別に測定する。多くのプロンプトを拒否する形式解析器で
  あっても、受理したプロンプトが信頼できるのであれば価値がある。

## 現在の実装との対応

現在の具体的な Planner:

- `DeterministicRecognizerPlanner`: 既知のプロンプトパターンに対する厳格な
  基準実装。
- `LLMFreeformPlanner`: 文法修復と任意の判定器を備えた汎用モデル。
- `AutoPlanner`: 認識器の高速経路の後、`LLMFreeformPlanner` にフォールバック
  する (S2)。

予定されている戦略の枠:

- `InteractiveStructuringPlanner`: ユーザー向けの明確化セッションを包み、
  その後、別のコード生成器に委譲する。
- `SpecializedCodegenPlanner`: 専用の命令型コードモデルを呼び出し、再試行は
  主に検証器のフィードバックに依存する。
- `FormalSemanticPlanner`: 制限された自然言語を意味形式へ構文解析し、
  制限付き命令型コードを出力する。

予定されている各戦略はいずれも、制限付き命令型コードを返し、
`pauth.prepare()` を通過しなければならない。いかなる戦略にも、rule を直接
出力することは許されない。
