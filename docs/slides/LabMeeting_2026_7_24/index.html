Next goal

Future work

The ultimate goal is AVAIL_4 = 100% with FN = 0, as cheaply as possible.

Future work · 1 / 4

Reduce reliance on human confirmation

Use confirmation only as an escape hatch; move repeatable cases into static authorization.

Problem

Some tasks depend on runtime values and currently require a human gate.

Next step

Extend the DSL, Planner, and Rule compiler so more of these tasks compile into static PAuth rules.

Success: fewer confirmations and higher AVAIL_4, while FN = 0 holds.

Future work · 2 / 4

Confirmation UX

A secure confirmation gate fails if users learn to approve every request.

Problem

Frequent or attacker-amplified prompts create confirmation fatigue.

Next step

Batch related actions, expose control operands, and rate-limit requests.

Success: fewer confirmations without lowering decision quality.

Future work · 3 / 4

Safe rule updates

Long-running tasks need authorization rules to evolve without inheriting authority from untrusted data.

Problem

Re-planning from runtime content can turn attacker input into permission.

Next step

Accept authenticated user updates, compile a new rule set, and retire the old one.

Success: no privilege carry-over between rule versions.

Future work · 4 / 4

Other framework

There are other frameworks for agents' tests.

Problem

Prompt capture, side channels, and evolving SaaS state remain under-tested.

Next step

InjecAgent / τ-bench / ToolSandbox / BrowserGym / WebArena / WorkArena / OSWorld / etc.

Final goal: guarantee performance for arbitrary user-authored prompts.
