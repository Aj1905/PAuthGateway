# 自己ホスト型ゲートウェイの方向性

本書は、現在の PAuth ゲートウェイを、既存のエージェント利用者が日々のエージェント作業の流れを変えずに接続できる自己ホスト型アプリへと転換するための、製品目標と工学上の境界線を記録する。

## 目標

利用者に、エージェントのプロンプト、エージェントのコード、tool 定義のいずれの編集も求めない。目標は次のとおりである。初期設定の後、利用者の普段のエージェント作業の流れは何も変わらないように感じられ、その裏側でゲートウェイがすべての外向きの動作を観測し、強制する。

初期設定にはゲートウェイ統合のインストール/有効化が含まれてよい。実際にはこれは次の両方を意味する。

1. 素のユーザープロンプト(clean prompt)と試行された tool 呼び出しをゲートウェイへ転送するライフサイクルフック/プラグイン。
2. エージェントが外向きの動作でゲートウェイを迂回することを防ぐネットワーク/tool 経路。

この目標が成り立つのは、ゲートウェイが次の二つを観測できる場合に限られる。

1. tool 結果の注入が計画に影響を及ぼす前の、利用者のタスクプロンプト。
2. 具体的な tool 名と引数を伴う、すべての外向きの tool 呼び出し。

対象のエージェントがこのいずれかを暗号化し、隠蔽し、あるいはフック/プロキシで観測可能なプロトコル境界を通さずに内部で実行するなら、透過的なネットワーク設定だけでは PAuth の強制は提供できない。せいぜい宛先単位の粗い許可/拒否を提供できるにとどまる。

## 設定の境界

近い将来における最良の製品上の約束は「設定ゼロ」ではない。次のものである。

- **エージェントのコード変更なし**: エージェントのバイナリ/ランタイムは無改変のまま。
- **プロンプト作業の変更なし**: 利用者はこれまでどおりエージェントにタスクを入力し続ける。
- **ゲートウェイの設定は一度だけ必要**: フック/プラグインのインストール/有効化、ゲートウェイ URL の設定、strict/log モードの設定、登録済み tool/API 呼び出しのゲートウェイ経由への経路設定。
- **健全性の可視化**: フックと tool 経路が有効かどうかをゲートウェイが可視化しなければならない。無言の故障は無防備よりも悪い。

より軽い設定をうたう代替案はいずれも弱い。

| 代替案 | 不十分な理由 |
|---|---|
| 純粋なネットワーク/TLS プロキシ | 素のプロンプト、意味のある tool 名、構造化された引数を復元できないのが通例。 |
| SaaS 側のみでの強制 | すべての SaaS が PAuth を採用するか、互換のポリシーフックを公開する必要がある。 |
| エージェントベンダーによる純正統合 | 使い勝手は最良だが、ベンダーの採用に依存し、自己ホスト側から制御できない。 |
| ブラウザ/OS の観測のみ | 壊れやすく、決定的かつ移植可能にするのが難しい。 |

したがって実用的な構成は**ゲートウェイアプリとエージェント統合の組み合わせ**である。ネットワークファイアウォールだけが安全性の境界なのではなく、ライフサイクルフックが PAuth の必要とする意味のある事象を供給する。

## 保護の前提条件: 生のサイドチャネルを持たないこと (Stage 1)

Stage 1 の保護の主張は、次の前提条件の下でのみ成り立つ(決定記録: S6。ボトルネック #5)。

- エージェントが生の Bash、直接のネットワーク I/O、観測されない資格情報の経路を**持たない**こと。すべての外向きの動作はゲートウェイを通る tool 呼び出しである。
- この前提条件を満たさない配備(例: Bash を有効にした Claude Code)を L3 保護として売り出してはならない。実効的な保護水準を L1/L2 として正直に報告する。
- サイドチャネルを塞ぐ gate 機構(許可リスト / サンドボックス / ファイルシステム仮想化 / 応答書き換え)は Stage 6(Mode 2)の課題であり、Stage 1 には含まれない。

## Egress Lockdown: Stage 1 の前提条件を「仮定」から「強制」に変える

上記の前提条件「エージェントは生の Bash も直接のネットワーク I/O も持たない」を、**設定時に OS のネットワーク経路で**強制する。これがなければ前提条件は単なる仮定にすぎず、PreToolUse フックを迂回する経路(許可された tool が生成するサブプロセス、シェルに降りる MCP サーバー、注入により `curl` を exec する tool)が素通りする(ケース B)。

### 何をするか

エージェントアプリ(Claude Code / Codex など)を**専用の非管理者ユーザー**として実行し、そのユーザーの外向き通信を**ゲートウェイの host:port のみ**に制限する。まず専用ユーザーを作成する(管理者権限が必要)。

```
sudo useradd -m -s /bin/bash pauth-agent   # macOS: sysadminctl -addUser pauth-agent
```

続いて、設定の一環として、管理者権限で次を一度だけ実行する。

```
sudo AGENT_USER=pauth-agent GATEWAY_HOST=127.0.0.1 GATEWAY_PORT=8081 gateway/deploy/egress_lockdown.sh apply
```

`gateway/deploy/egress_lockdown.sh` はこれを、Linux では nftables/iptables の `uid-owner` ルールとして、macOS では pf の `user` ルールとして適用する。子プロセスは UID を継承するため、エージェントがどんなコマンドを発行しようと、プロセスツリー全体が同じ制限の下に置かれる。

適用状態の確認と解除には、同じスクリプトの `status` / `remove` を使う。

```
sudo AGENT_USER=pauth-agent gateway/deploy/egress_lockdown.sh status
sudo AGENT_USER=pauth-agent gateway/deploy/egress_lockdown.sh remove
```

適用後は、エージェントをその専用ユーザーとして実行する(例: `sudo -u pauth-agent claude`)。これで、そのユーザーが張るすべての外向き接続はゲートウェイの host:port にしか到達できず、それ以外はカーネルによって遮断される。

### 通信の中身を読めなくても遮断できる理由

宛先がゲートウェイに固定されてしまえば、迂回の試みの結果は二つしかなく、どちらも失敗する。

1. **外部ホスト宛て**(例: `curl bank.example`)→ このルールが**カーネル内で破棄する**。外に出ることはない。ゲートウェイが目にすることすらない。
2. **ゲートウェイ宛て**(唯一到達可能な宛先)→ ゲートウェイが受け取り、**デフォルト拒否**であるため、正当に認可された tool 呼び出しでないものはすべて拒否する。

したがってゲートウェイは、中身の見えない `curl` の**バイト列を解読する必要がない**。不透明な通信は「行き先がない(破棄)」か「デフォルト拒否のゲートウェイに届く(拒否)」かのいずれかであり、常に安全側(遮断側)に倒れる。これは「解読するのではなく無力化する」設計であり、実効的な保護を正直な L0/L1 から L2/L3 へ引き上げるための土台である。

### 管理者権限を与えるとこれは迂回される(明記必須)

**この制御は「エージェントがルールを削除できない」ことの上にのみ成り立つ。** エージェントを root / 管理者 / sudo 可能なユーザーとして実行すると、エージェント(または注入によって実行させられたコード)はファイアウォールルールを消去し、外部サーバーへ直接到達し、**ゲートウェイを迂回**できる。スクリプトは対象が root の場合には適用を拒否し、適用後にこの警告を表示する。**エージェントに管理者権限を与えてはならない。** 与えた瞬間にこの制御は無効となり、実効的な保護水準は L1/L2 として正直に報告しなければならない。

### 対象外のもの(別途対処する)

- **ネットワーク以外の副作用**(ローカルファイルの改竄、秘密情報の仕込み)は egress 制限では防げない。ファイルシステム側で別途制約する。
- **ゲートウェイ自身の egress**: ゲートウェイは実際の SaaS に到達する必要があるため、このルールに掛からないよう、エージェントとは**別のユーザー**として実行する。
- DNS / IPv6 / QUIC (UDP): スクリプトはエージェントの外部 DNS、IPv6、UDP もまとめて破棄する(実際の呼び出しはゲートウェイが行うため、エージェントに外部 DNS は不要である)。自前のリゾルバに固定した DoH を使うクローズドソースのコードには、その DoH 宛先の遮断が別途必要になる。

## プロンプト捕捉の境界

あらゆるエージェントから単一の機構でプロンプトを捕捉することは現実的ではない。目標は「同じ捕捉機構」ではなく「捕捉後に同じ正規化済み事象になること」である。

すべての統合は、エージェント固有のプロンプト信号を次の形に変換すべきである。

```json
{
  "kind": "prompt",
  "session_id": "agent-session-id",
  "prompt": "clean user task text",
  "source": "claude-code-hook | mcp-session | browser-extension | desktop-plugin | manual",
  "captured_before_model": true
}
```

現在のコードは、正規化済みプロンプト事象として `gateway/ingress/agent_channel.py` の `PromptMessage` を用いている。今後のプロンプト捕捉アダプタも同じ境界に流し込むべきである。

プロンプト捕捉の選択肢を、強い順に並べる。

| 捕捉経路 | 強さ | 問題 |
|---|---|---|
| エージェントのライフサイクルフック/プラグイン | 利用できる場合、近い将来の最良の経路。tool 実行前にプロンプトを捕捉できる。 | エージェントごとの統合作業が必要。 |
| ゲートウェイ自身が持つプロンプト入口 | 完全性は最も高い。利用者はまずゲートウェイを通してタスクを入力する。 | 利用者の作業の流れを変える。許容できる場合に限って使う。 |
| MCP/セッションのメタデータ | エージェントが tool サーバーにタスクのメタデータを送る場合には有望。 | 普遍的に利用できるわけでも、標準化されているわけでもない。 |
| ブラウザ/デスクトップ拡張 | フックを持たないエージェントの助けになりうる。 | 壊れやすく、アプリ固有で、順序性の証明が難しい。 |
| 手動確認への切り替え | 安全性が重要な動作には有用。 | 作業の流れを変え、手間を増やす。 |

ゲートウェイはセッションごとに保護水準(L0–L3)を追跡すべきである。**L0–L3 の正準定義はコード `gateway/runtime/protection.py` の `ProtectionLevel` である**(人間向けの一覧表は `DESIGN_STATUS.md` の「現在の保護モデル」にある)。ここでは要点のみ述べる。

- **L2 未満のものを「完全な保護」と呼んではならない。** PAuth 流の主張は L2(素のプロンプト + tool 呼び出し)から始まり、設計目標は L3(+ tool を実行するゲートウェイ)である。
- 素のプロンプト捕捉または経路制御を欠くセッションは、完全な PAuth 保護として売り出さない。

## 構成の形

```text
agent runtime
  |
  | hook/plugin + network/tool route
  v
gateway ingress
  |
  | normalized PromptMessage / ToolCallMessage
  v
Planner boundary
  |
  | restricted imperative code
  v
pauth.prepare() -> rules
  |
  | per-call enforcement
  v
upstream tool/SaaS/MCP server
```

安定した契約は、この正規化済みメッセージ境界である。

- `PromptMessage`: タスクプロンプトと Planner のオプション。
- `ToolCallMessage`: 具体的な tool 名と、その順序付きまたは名前付きの引数。

この境界より前はすべてアダプタ/プロキシの仕事である。Planner 境界より後はすべて PAuth の決定的な核である。

## Planner の選択

自己ホスト配備は、配備またはセッションごとに Planner 戦略を選ぶ。現在の
`PAUTH_PLANNER_STRATEGY` の値、既定値、必須設定は `gateway/hooks/README.md` §3、
正準名と生成処理は `gateway/planning/planner.py` を正とする。本書では一覧を
複製しない。

各戦略(`P3`–`P5` を含む)の状態と契約は `SYSTEM_MODEL.md` 第 2 部
Planner の節の登録表に置く。将来の設定ファイルや UI も同じ正準名を使い、
`SYSTEM_MODEL.md` の Planner 境界を変えない。

## 自己ホストの基盤

最小の自己ホスト型アプリ:

1. **設定可能な上流レジストリ**
   - MCP/HTTP/SaaS 向けのツールアダプタを登録する。
   - tool スキーマ、パラメータの順序、返り値スキーマを保持する。
   - 明示的に名前空間を分けない限り、tool 名の衝突を拒否する。
   - HTTP API については、OpenAPI 仕様をツールアダプタの契約に反映する。
   - 上流 API 仕様の変化を検出し、新しい tool 面を受け入れる前に利用者へ通知できる報告を発行する。

2. **Ingress アダプタ**
   - tool 境界を観測できる MCP/HTTP から始める。
   - Claude Code フックは製品の核ではなく、互換アダプタとして維持する。
   - プロトコル固有のアダプタは、エージェントによる書き換えを信頼せずにプロンプトと tool 呼び出しを露出できる場合に限って追加する。

3. **Planner プラグイン境界**
   - Planner を配備/セッション単位で選ぶ。
   - 生成コード、検証失敗、再試行履歴を監査用に保存する。
   - 本番の既定の姿勢は、でっち上げではなく「不確かなら拒否」であるべきだ。

4. **セッションと監査の保存**
   - プロンプト、選ばれた Planner、生成コード、コンパイル済みルールの要約、判定、拒否、上流呼び出しの結果を永続化する。
   - envelope の署名鍵は配備の内部に留める。

5. **運用面**
   - ツールアダプタと Planner モードのための単一の設定ファイル。
   - 上流 tool と Planner 資格情報の健全性検査。
   - 導入時のツールアダプタ単位の strict/log モード。
   - 設定済み OpenAPI アダプタに対する定期的な API 仕様監視。

## API 仕様の反映と変更通知

OpenAPI に基づくスイートはゲートウェイ設定に登録できる。

```json
{
  "merged_suite_name": "user_default",
  "suites": [
    {
      "name": "billing",
      "kind": "openapi",
      "spec_path": "billing.openapi.json",
      "base_url": "https://api.example.com"
    }
  ]
}
```

ゲートウェイ起動時に、`gateway/providers/openapi_suite.py` が現在の OpenAPI 文書をツールアダプタの契約に反映する。operation は tool になり、パラメータと JSON ボディのフィールドはその tool のオペランドになり、レスポンススキーマは Planner の tool ドキュメントになる。

通知/更新の作業の流れには、次を実行する。

```bash
.venv/bin/python -m gateway.api_spec_monitor \
  --config gateway.json \
  --state .gateway/api-spec-state.json \
  --update
```

この監視器は、変化した仕様、追加/削除された tool、変化したパラメータ一覧を記述する JSON を出力する。自己ホスト配備では、その JSON をメール、Slack、アプリの UI 通知、あるいは再起動/再読み込みの作業の流れにつなげられる。

現在の制限: 稼働中の `gateway/serving/http_server.py` は、変更された OpenAPI 仕様をホットリロードしない。次の層では、認証付きの再読み込みエンドポイントか、変更後の tool 面を利用者が受け入れた後に監督プロセスが管理する再起動を追加すべきである。

## 現在の配備形態: Sakura 上のセルフホスト、Monocle による管理(短期)

抽象が特定の配備先へ漏れ込まないこと(`SYSTEM_MODEL.md` 第 6 部の不変条件
「すべての抽象は配備境界の上に載っている」)を原則として保つ。以下は現行の
具体形態である。

```
                         ┌──────────────────────┐
                         │  USER (laptop / SSH) │
                         └──────────┬───────────┘
                                    │  ssh / web shell
                                    ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │ Sakura Internet VM   (provisioned and managed by Monocle)       │
   │                                                                 │
   │  ┌─────────────────────────────────────────────────────────┐    │
   │  │  systemd unit: claude-code                              │    │
   │  │   └─ hooks: submit_prompt.sh / pretool.sh               │    │
   │  └────────────┬────────────────────────────────────────────┘    │
   │               │ localhost HTTP (127.0.0.1:8081)                 │
   │               ▼                                                 │
   │  ┌─────────────────────────────────────────────────────────┐    │
   │  │  systemd unit: gateway-http                             │    │
   │  │   - gateway/serving/http_server.py --config /etc/gateway.json   │    │
   │  │   - in-memory sessions, restart loses state             │    │
   │  └────────────┬────────────────────────────────────────────┘    │
   │               │                                                 │
   │     ┌─────────┴───────────────────────┐                         │
   │     │ stdio subprocess MCPs           │ HTTP MCPs              │
   │     ▼                                 ▼                         │
   │  ┌────────────────────┐   ┌────────────────────────────────┐    │
   │  │  @mcp/filesystem,  │   │  internal MCP HTTP shims,      │    │
   │  │  @mcp/git, etc.    │   │  bound to 127.0.0.1            │    │
   │  └────────────────────┘   └─────────────┬──────────────────┘    │
   │                                         │ outbound HTTPS         │
   └─────────────────────────────────────────┼────────────────────────┘
                                             │
                                             ▼  (Sakura egress, private route preferred)
                                ┌────────────────────────┐
                                │  public SaaS APIs       │
                                │  (Gmail, Linear, ...)   │
                                └────────────────────────┘
```

運用上の選択:

* **1 VM、1 ゲートウェイ、1 ユーザー。** この段階ではマルチテナントは対象外。
  セッションの分離は Claude Code の ``session_id`` による。
* **状態。** セッションはプロセスのメモリ上にあり、``systemctl restart`` で
  失われる。ユーザーがプロンプトを出し直せば済むうちは許容する。長時間走る
  タスクが現実のものになったら見直す。
* **秘密情報(credential broker モデル、S4)。** ゲートウェイが SaaS の資格情報を
  **保持し、実行する**。このモデルの定義と、旧モデルを破棄した論拠は
  `SYSTEM_MODEL.md` 第 1 部「Credential broker(S4)」を正とする。ここで
  決めるのは配備上の受容だけである: 鍵の集約点になる危険は、このセルフホスト
  形態(ユーザー自身の VM 上で動く 1 VM / 1 ユーザー)を前提とすることで
  受け入れる。broker 実装の要件: スイートごとに分離した保管、ローテーション、
  アクセス監査。(実装は最初の実 SaaS 統合と併せて行う。)
* **ネットワーク。** ``gateway-http`` は ``127.0.0.1`` に束縛されるため、HTTP
  API に外部から到達することはできない。hook はローカルなので到達できる。
  ローカル区間に TLS はない。公開 SaaS への外向き通信は、Sakura の標準の
  egress と、Monocle が提供する私設経路を併用する。
* **ログ/可観測性。** ゲートウェイと hook スクリプトは stderr に書き、
  systemd の journal がそれを捕捉し、Monocle が journal を集約する。
* **バックアップ/復旧。** セッションは揮発とする。設定とスイート登録は平文の
  ファイルであり、Monocle の VM イメージ管理が面倒を見る。
* **更新。** アプリケーションは VM 上の Python ソースである。更新の適用は
  ``git pull`` + ``systemctl restart gateway-http``、(hook スクリプトが変わった
  場合は)Claude Code の設定の再読み込み。

利点と欠点:

* (+) 安価で、全体を自分たちで掌握でき、hook 呼び出しの遅延が小さい。
* (+) 特定の業者への束縛がない。スタック全体が Linux VM 上のファイルにすぎない。
* (-) 単一障害点。VM が 1 台落ちれば Claude Code が使えなくなる。
* (-) 拡張は手作業。1 ユーザーには十分だが、多数には耐えない。

## 運用上の注意

* Claude Code を開く前に、ゲートウェイのデーモン
  (`gateway/serving/http_server.py`)を起動すること。session store を有効にした
  配備では、再起動時に plan fingerprint と実行試行を復元し、`succeeded` /
  `indeterminate` call の再 dispatch を拒否する。EnvelopeStore と HMAC 鍵は
  まだ復元しないため、再起動前の結果に依存する後続 call は fail-closed となり、
  シームレスには続行できない。session store が無効なら、再起動時に active
  session は失われる。
* JSON の `SessionStore` は単一 Gateway プロセス用である。active-active 配備で
  同じ session を複数プロセスが処理する場合は、operation ID に対する conditional
  write / CAS を持つ共有データストアが必要であり、JSON ファイルの共有では
  at-most-once を主張できない。

## 最初の版で目指さないこと

- 任意のエージェントに対する汎用の TLS MITM。運用上壊れやすく、それ単体では意味のある tool 名や引数を復元できない。
- プロンプトからコードへの変換の正しさに関する主張。PAuth は生成された計画を強制するのであって、その計画が利用者の意図を忠実に捉えていることを証明するのではない。
- 完全な SaaS マルチテナントホスティング。近い将来の目標は、自己ホストの単一利用者または単一チームの配備である。

## 直近の工学的順序

1. `pauth/` を安定かつフレームワーク中立に保つ。
2. すべての Planner 変種を `gateway.planner` の背後に移す。
3. `AgentChannel` の JSON メッセージを内部の正規化済みプロトコルとして扱う。
4. 実際のエージェント通信をそのプロトコルへ変換する ingress アダプタを作る。
5. 正規化済みプロトコルが安定した後に、永続化/監査を追加する。
