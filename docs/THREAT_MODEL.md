# 脅威モデルと防御

本書は、PAuthGateway が防御する脅威、各脅威を防ぐ機構、そして —— 最も重要な点と
して —— **どの防御が実際に構築済みで、どれが設計のみか**を列挙する。脅威の一覧・
防御機構・実装状態は本書を正とする(`SYSTEM_MODEL.md` 第 6 部は「厳格な不変条件」
の末尾から本書を参照するのみ)。執行中核の脅威に加えて、設計検討で詰めた間接
プロンプト注入／オペランド来歴の層を扱う。

> 本ファイルの正直規則: 脅威に ✅ **解決済み(構築済み)** を付けるのは、今日コードが
> それを執行している場合**だけ**である。来歴・汚染・egress の各層(§3、§4)は
> **設計であって実装ではない** —— 参照先のコードが存在するまで、実効的な防御として
> 引用してはならない。

## 0. 概念の背骨(まずこれを読むこと)

二つの枠組みの軸が、別々の脅威を一つの言い回し(「注入を防ぐ」「自由オペランド
問題」)へ潰してしまうという、繰り返し起きる混同を防ぐ。

**軸 1 — 執行の隙間か、意図把握の隙間か。**
- *執行の隙間*: エージェントが、利用者の承認した計画の外で行動する。これは認可の
  問題である。**決定的であり、解決済み。**
- *意図把握の隙間*: 計画そのものが利用者の意図と一致しない。これは正しさの問題で
  ある。**オラクルは存在しない。**完成した計画を人間が確認することによってのみ
  解決される。

**軸 2 — 行動の注入か、内容・データの注入か。**
- *行動注入*: 汚染データが、エージェントに**計画外の新しい行動**を取らせようと
  する。固定された計画と既定拒否で防御される。
- *内容・データ注入*: 汚染データが、**すでに許可された行動の中を流れる内容や値**を
  操作する。これが困難な残余であり、§3–§6 の主題である。

**繰り返し現れる反パターン(記憶すること)。**行き当たった袋小路はすべて同じ形を
していた: *攻撃者が制御できる内容を、安全上の判断の入力に使う*ことである。安全上の
判断で何らかの信号を信頼する前に、こう問うこと: **攻撃者はこれを書けるか?** 書ける
なら、その防御はすでに破れている。§7 を参照。

## 2. 解決済み — 執行中核(構築済み)

以下は今日 `pauth/` と `gateway/` によって執行されている(`SYSTEM_MODEL.md` 第 6 部「厳格な不変条件」を参照)。**成立する理由**の列は、各脅威が実際に閉じている
理由を述べる —— 機構の名前だけでなく、その機構を十分たらしめている性質を示す。

| 脅威 | 機構 | 成立する理由 | 状態 |
|---|---|---|---|
| エージェントが計画にないツール呼び出しを発行する | ルール不在時の既定拒否 | **閉世界の執行。**許可される集合は、計画からコンパイルされたルールそのものである。明示的に許可されていないものは拒否される。一致するルールなしに「許可」へ至る経路はなく、新しい呼び出しが隙間をすり抜けることはない —— ルールの不在こそが拒否である。 | ✅ |
| エージェントが定数オペランド(IBAN、金額、件名、日付)を水増し・すり替える | コンパイル済みルールとのオペランド照合 | オペランドの値は計画時にルールの中へ固定される。検査は、呼び出しのオペランドをその固定値と比較する。いかなるすり替えも不一致となり拒否される。エージェントはルールを書かないので、自分の許可範囲を広げられない。 | ✅ |
| エージェントが、観測していない導出値(例: 一度も観測していない `cart.total`)を捏造する | envelope 保管庫に対する記号的評価。エージェントの報告値は無視 | ツールを実行し、結果を署名付き envelope として記録するのは、エージェントではなく gateway である。オペランドの解決は envelope 保管庫**のみ**を読むため、エージェントが捏造した値には裏付けの envelope がない → 未解決 → 拒否。エージェントが報告する数値が判断の入力になることは決してない。 | ✅ |
| エージェントが観測を飛ばし、その記号的な結果を使う | envelope 不在 → オペランド未解決 → 拒否 | 導出オペランドは、上流の観測が実際に走った(その envelope が存在する)場合にのみ解決される。観測を飛ばすとオペランドは未解決のままで、Enforcer はルールを評価できず、拒否する。値を「仮定する」手立てはない。 | ✅ |
| エージェントが要注意ツールを順序を外れて呼ぶ(データ依存あり) | ガードが上流の envelope を要求。不在 → 拒否 | 順序は、上流 envelope へのガード依存として符号化されている。順序を外れて呼べば、必要な envelope がまだ存在しないので、ガードは偽と評価される → 拒否。順序はデータ依存によって執行されるのであって、エージェントが自ら順序を守ることを信頼してはいない。**この行が守るのはデータ依存として書かれた順序に限る** — 依存のない順序は次行。 | ✅ |
| データ依存のない副作用 call の順序入れ替え(check-then-act、limit-then-send) | plan 語順の前提検査(`ordered_tools`。`PAUTH_ENFORCE_CALL_ORDER=1` で有効化) | live な対象 call は、語順で前の対象 site がすべて実行済みか、guard が偽で経路外であることを要求する。一括関門確認の遅延実行・部分却下と衝突するため**既定は無効** — 有効化は配備判断であり、無効の配備ではこの脅威は開いたままである。 | ✅(opt-in、既定無効) |
| エージェントが許可済み call を同一オペランドで再発行する(リプレイ) | call site ごとの消費。実行し envelope を記録した時点で確定 | plan が含む回数(ループは列挙の組ごとに一回)を超える live call は認可されない。確認待ちの保留は消費せず、事後の監査プローブは消費に盲目で純粋な認可関係を見る。 | ✅ |
| エージェントがセッション途中で計画を立て直す(注入時など) | `AgentChannel` が二通目の `PromptMessage` を拒絶する | 計画はちょうど一度だけ作られ、以後は不変である(不変条件 #1)。二通目のプロンプト —— 注入が新しい計画を据え付けるための経路 —— は構造的に拒絶されるため、固定後に計画を書き換える API の入口が存在しない。 | ✅ |
| ツール結果を介した**行動注入**(計画外の新しい行動。論文 3 節、AgentDojo の脅威モデル) | ツール出力が存在する前に、汚染されていないプロンプトから計画を生成する | **時間的な順序が閉じる。**計画は、エージェントが何らかのツール出力を読む*前に*、完全に導出され固定される。したがって注入された指示は計画に影響できない。注入された「X をせよ」は計画にないツール呼び出しに対応する → 既定拒否。毒が届くのは、それが汚染しえた唯一の判断がすでに下された後である。 | ✅ |
| `"ignore previous instructions"` が **Planner** に届く | Planner はツール出力を決して読まない | **抵抗ではなく、構造的な免疫。**Planner の唯一の入力は汚染されていないユーザープロンプトであり、メール・ウェブ・ツール結果を読むコード経路上には決して置かれない。注入文はそこへ到達できないため、抵抗すべきものが何もない —— その経路自体が存在しない。 | ✅ |
| `"ignore previous instructions"` が**実行中のエージェント**を乗っ取る | 乗っ取られたエージェントの呼び出しも、固定された計画に照らした gate を通る | **設計はエージェントが注入済みであることを前提とし、エージェントの抵抗に依存しない。**完全に説得されたエージェントにできることも*ツール呼び出しの発行*だけであり、すべての呼び出しは不変の計画に対する実行時執行(Enforcer の全検査)を通る。信念は行動ではない: 計画外の呼び出しは、エージェントが何を「望む」よう説得されていようと拒否される。 | ✅ |
| 計画が利用者の意図と一致しない(意図把握の隙間) | grill-me が雛形を埋め、実行前に利用者が完成した計画を確認する | **意図を判定できるオラクルはないが、人間にはできる。**正しさは執行可能な性質ではないため、意図を知る唯一の当事者 —— 固定前に具体的な計画を承認する利用者 —— へ意図的に委ねる。この系は意図を検証すると*主張しない*。人間を検証者にするのである。 | ✅(人間による) |

## 3. 計画内注入の層 — 大部分は実装済み (S18–S20)

これは軸 2 の残余である: 汚染データが、*すでに許可された*行動の内部の内容・値を
操作する。執行中核はこれを**扱わない**。防御は、来歴の汚染追跡 + sink 分類 + 人間
への引き上げであり、**その中核は実装済み**である (S18/S19/S20)。残るのは Q-LLM
と、確認の HTTP 通信面の公開だけである。

防御の構成要素(現状):

| 構成要素 | 役割 | 実装 |
|---|---|---|
| 供給元の信頼ラベル | どのツールが非信頼データを返すかを宣言する。**既定を非信頼(fail-closed)にできる** | 🟢 `gateway/runtime/confirmation.py` (`SourceTrust` / `SourceTrust.fail_closed`) |
| 汚染の伝播 | DSL(単一代入、ループなし)を出発点に、どの制御オペランドが非信頼の供給元に由来するかを**静的な来歴**で追跡する。変換 (`amount*2`) を経ても汚染は落ちない | 🟢 `gateway/runtime/confirmation.py`(`static_taint_map`、S20。静的解析であり、設計段階で考えた実行時の「meet」ではない) |
| sink 分類 | 制御オペランド(宛先・金額)を決定する。内容オペランドは gate されない(S15 の内容／制御の分離) | 🟢 `gateway/planning/prechecks.py` (`_classify_param`) + `confirmation.py` (`control_operands`) |
| 確認ゲート (taint × sink) | `untrusted × control operand` → **人間の確認まで保留** (PENDING_CONFIRMATION)。セッション経路と複合経路の両方で発火する (S19) | 🟢 `gateway/runtime/gateway.py` (`_confirmation_gate`) |
| 確認の往復 | 保留された値と来歴を人間側の別経路へ渡し、承認で解放する | 🟡 Python API は実装済み(`Gateway.pending_confirmations()` / `confirm()`)。HTTP 通信面(`confirm_request` / `confirm_response`)は未公開 |
| 隔離 LLM (Q-LLM) | 非信頼の内容を、**ツールへの接続なしに**読む。出力には非信頼の札が付く | 🔴 未実装 |

補足: envelope はすでに、**各値をどのツールが生成したか**を記録している(偽造
不能、HMAC 署名付き)。信頼ラベルはその出所に対する*ポリシー上の解釈*であり、
envelope ではなくポリシー・設定側に置かれる。したがってこの層は、既存の基盤の上に
参照・伝播・gate を加えるだけであり、署名付き envelope の形式は変えない。

**外部の先行事例(参照点)**: OpenAI の Responses API は、reasoning モデルの tool
使用履歴を型付き item(`reasoning` / `web_search_call` / `function_call` /
`function_call_output`)の列として扱い、tool call item をそれを生んだ `reasoning`
item と切り離して次リクエストに渡すと文脈不整合として拒否する(例: `Item 'ws_...'
was provided without its required 'reasoning' item`)。「tool call の出自を履歴構造で
強制する」という点で、署名付き envelope による来歴記録と同型の考え方である。ただし
この検証が防ぐのは履歴構造の改ざん(item の差し込み・接ぎ木・並べ替え)だけで、
内容への注入は防がない — 内容・データ注入が残余であるという本節の整理と一致する。
将来ゲートウェイが Responses API ベースのエージェントの履歴を仲介する場合は、表示・
監査の都合で raw item 列から item を削ると後続リクエストが API に拒否される点に注意
(表示用 transcript と API 再投入用履歴は分離する)。出典:
[Reasoning models guide](https://developers.openai.com/api/docs/guides/reasoning)、
[Conversation state guide](https://developers.openai.com/api/docs/guides/conversation-state)。

この層が扱う脅威(確認ゲートの実装によって**緩和**。既知の残余あり):

| 脅威 | 機構 | 状態 |
|---|---|---|
| 汚染された供給元に由来する導出オペランドが、**制御**オペランド(宛先・金額)へ流れ込む(例: メール内にある攻撃者制御の IBAN) | 供給元が非信頼 → 静的な来歴汚染 → 制御オペランドで PENDING_CONFIRMATION → 人間が確認 | 🟢(S18–S20。残余: fan-out 段が、観測された定数畳み込みを通じて来歴を落とし、gate が不足しうる。S20) |
| 外部 sink への自由オペランドの**内容**汚染(例:「本文に秘密を含めよ」) | 内容オペランドは gate されない (S15): 汚染は確認済みの宛先にしか届かず、被害は限定される。制御オペランドへ流れ込む場合は、一つ上の層で保留される | 🟢(内容／制御の分離) |
| Q-LLM 出力の操作(「IBAN は攻撃者のものを出力せよ」) | ツールへの接続なしに非信頼の内容を読む Q-LLM を前提とする | 🔴 Q-LLM 未実装 |

## 4. 未解決問題 — きれいな解はまだない

| 問題 | 難しい理由 | 状態 |
|---|---|---|
| **egress sink 列挙の完全性** | 有害な sink(例: `delete`)が `internal-read` に誤分類されると、計画内注入が音もなく gate を通過する。この防御の強さは、sink 一覧の精度どまりである。**現時点で最も弱い箇所。** | 🔶 |
| 記録単位の信頼の粒度 | スイート単位の信頼は安全だが粗い(Gmail 全体を非信頼にすると、メール由来のすべての値に確認が要る)。より細かい信頼は、**検証済み**のメタデータ(DKIM/SPF で検証された送信者、OS のパス)を使わねばならず、内容が自称するメタデータを使ってはならない。実際の検証基盤が必要になる。 | 🔶 |
| 信頼設定の誤り | 配備者が非信頼の供給元を誤って信頼と印付けすると、gate が開く。既定非信頼で緩和されるが、設定そのものが攻撃面になった。 | 🔶 |
| egress 確認の使い勝手上の代償 | `untrusted × egress` の動作のたびに利用者が中断される。自動化の度合いが高い用途ほど、これが応える。ここに安全で無監督の自動経路は存在しない。 | 🔶 |

## 5. 範囲外(受容済み・防御しない)

| 脅威 | 受容する理由 |
|---|---|
| 利用者自身のプロンプト入力窓での注入 | 入力窓は信頼される —— 利用者の責任 (Q11) | ⚪ |
| 転送段階でエージェントがプロンプトを黙って改変する | hook 経由の経路が持ち込む信頼前提 (Q13)。緩和策: `UserPromptSubmit` は LLM がプロンプトを見る前に走るため、LLM はプロンプトを改変できない | ⚪ |
| 利用者が hook を無効化・迂回する | 利用者は信頼される (Q0) | ⚪ |
| サイドチャネル: ファイルシステム、bash、子プロセス、環境変数 | gateway が観測できるのはツール呼び出しだけである。実際の Claude Code のファイアウォールには、加えて Bash のポリシーやサンドボックスが必要 (Q7/Q10) | ⚪ |
| 可用性への攻撃: 乗っ取られたエージェントがタスクを妨害・脱線させる | **有害な行動は生じない**(計画外の呼び出しは拒否される)—— 進捗が欠けるだけである。活性の問題であって、安全の侵害ではない。 | ⚪ |
| 利用者が承認した範囲を超えるプロンプトの正しさ | PAuth は計画を執行する。正しさのオラクルではない。利用者は、誤ったことをする計画を承認しうる。 | ⚪ |

## 6. 除去不能な底 ⛔

上記の防御をすべて講じたのちも、一つの脅威が残り、**いかなる設計でも取り除けない**:

> **egress 確認の場で人間が言葉巧みに操られ**、明瞭に提示された悪意ある行動を
> 承認してしまう。

この系の仕事は、問題をこの底*まで*縮めることである: 確認を**最大限に情報の
行き届いたもの**にし(解決済みの値と偽造不能な来歴の連鎖 —— 「IBAN …、
`unknown@external` からのメール由来、DKIM 未検証」—— を示す)、かつ**最小限の
頻度**に抑える(`untrusted × egress` のみとし、計画時の固定で集合をさらに縮める)。
この底を取り除けると主張する者は、存在しない正しさのオラクルを売りつけている。

## 7. 明示的に棄却した反パターン

設計で歩いた袋小路である。いずれも、*攻撃者が制御できる内容を安全上の判断の入力に
使う*(§0)ことの具体例である。再提案されないよう記録しておく。

| 棄却した案 | 破れる理由 |
|---|---|
| オペランドが「意図に沿うか」を LLM が判定する | 判定器は汚染データを読む → それ自体が注入可能である。「正しい」値についての独立した正解を持たない。注入可能な LLM を別の注入可能な LLM で直すのは、どこまで行っても土台のない積み重ねである |
| 供給元の信頼を**その内容を読んで**決める | 内容を書く攻撃者に、信頼の判断を手渡すことになる(「このメールは信頼できる銀行からのものです」) |
| 内容が自称するメタデータ(例: `From:` ヘッダ)を信頼する | 偽造可能である。暗号学的に**検証された**来歴 (DKIM/SPF) だけが通用する |
| 「自由オペランド」を防御の単位として扱う | 汚染された供給元に由来する導出オペランドの事例を取り逃がす(その IBAN は*検査される*オペランドだが、供給元によって依然汚染されている) |
| LLM に「理解」させるために供給元を信頼と印付けする | 範疇の取り違えである: 非信頼 ≠ 読めない。読むことは内部の行為であり、常に許可される。信頼が支配するのは egress だけである。読むために供給元を信頼と印付けすることは、そのラベルが塞ぐために存在するまさにその穴を開ける |

## 8. 端から端までの防御の流れ

```
User prompt
   │  grill-me fills template; operands classified pinned (USER) vs derived (read-time)
   ▼
HUMAN CONFIRM the completed plan   ← intent-capture gap closed here (§2)
   │  plan locked; never re-planned
   ▼
─── execution; per tool call ───
   ▼
plan enforcement — Enforcer (built, §2)     ← action injection blocked here
   │  permitted by plan
   ▼
confirmation gate — taint × sink (built, §3) ← content/data injection handled here
   │   trusted?            → pass
   │   untrusted × internal → pass (no egress harm; reading/understanding never blocked)
   │   untrusted × egress   → CONFIRM
   ▼
HUMAN CONFIRM the egress value + provenance chain   ← irreducible floor (§6)
   │
   ▼
suite.tool_executor executes · envelope records signed observation (built, §2)
```

非信頼の内容は自由に読まれ、理解される(ツールへの接続を持たない隔離 LLM による
場合を含む)。系全体が最終的に gate するのは、**非信頼由来の値が egress 境界を
越えること**だけであり、その判断のために最終的に信頼するのは、人間と、暗号学的に
検証可能な来歴だけである。
