# PAuth 論文を書く

正本と再現可能な証拠から論文を書く。既存原稿は証拠でも用語の正本でもない。

## 必須契約

- リポジトリのルートで作業する。最初に `AGENTS.md` と `docs/SYSTEM_MODEL.md` を全文読む。用語をスキル内の記憶や既存原稿から補わない。
- 執筆対象に応じて `docs/EVALUATION.md`、`docs/THREAT_MODEL.md`、`paper/README.md`、評価結果、実装、テスト、書誌を読む。存在しない案内先や古い生成物を根拠にしない。
- 一般的な日本語は平易に使う。「リポジトリで定義された語だけ」とは、PAuth 固有、論文固有、一般読者に馴染みの薄い専門概念を正本へ拘束する規則として扱う。自然言語の全単語を許可リスト化しない。
- 事実、測定結果、推論、著者の動機を分ける。著者の着想や個人的経験が記録にない場合は創作せず、本人へ確認するか未確定箇所として残す。
- 数値を既存原稿から転記しない。原データ、再現コマンド、版、分母、設定、ソース状態を確認する。成果物が古い、欠けている、未追跡、または現在のコードと不整合なら、その数値を確定結果として扱わない。
- 依頼された原稿と、その原稿で必要になった正本だけを変更する。作業ツリーにある他人の変更を上書きしない。

## 作業手順

### 1. 対象と証拠状態を固定する

1. 対象ファイル、言語、投稿形式、章、中心的な問い、今回変更する主張を特定する。
2. 日本語 Markdown と英語 LaTeX を別原稿として扱う。内容が同期していると仮定しない。
3. 次の二つの台帳を作業メモに作る。

| 主張 | 証拠ファイルと位置 | 実行条件・版 | 許される強さ | 未解決点 |
|---|---|---|---|---|
| 専門語 | 正本の位置 | 初出の定義文 | 初出位置 | 状態 |

4. 中心的な主張には、原データまたは再現可能な結果を割り当てる。実装だけから性能を推定しない。

### 2. 用語を先に解決する

1. 本文で使う専門語候補を抽出し、`docs/SYSTEM_MODEL.md` と照合する。PAuth の部品や指標だけでなく、製品名、モデル名、ベンチマーク名、統計検定名、論文内で導入する略語も候補に含める。著者名、所属、書誌情報、一般的なファイル形式は除く。
2. 正本にない専門概念は本文で使わない。必要なら先に正本の適切な部へ「日本語名 / 英語名」と平易な定義を追加する。正本の変更が依頼範囲を越える場合は、その概念を使う箇所の確定を止めて利用者へ伝える。
3. 初出時に「何であるか」と「何をする、または何を測るか」を一文か二文で説明する。定義文の中へ別の未定義専門語を入れない。
4. 初出後の地の文では日本語名を使う。英語名は定義行、バッククォート付きのコード・型名、図中の表記に限る。指標名と凍結済み版 ID は正確な綴りを使う。
5. 部品と成果物を分ける。PAuth パイプラインのノードは、計画器、文法検証器、スライサ、ルールコンパイラ、執行器、封筒保管庫である。実行部とツールアダプタをノードに数えない。
6. run コードの言語を DSL と呼ぶ。原論文版と現行版を比較する文では `DSL(G1)`、`DSL(G2)` のように版を付ける。ツール呼び出しを裸の `call` と書かない。
7. 計画生成エラー、DSL 棄却、拒否、クラッシュ、ツールエラー、ツール結果不明、実行状態障害、過剰、不足を入れ替えない。

### 3. 「はじめに」を因果で組み立てる

導入を書く前に [references/section-patterns.md](references/section-patterns.md) の「はじめに」を読む。次の因果を、読者が一度で追える順に置く。

1. 著者が直面した具体的な状況、観測、または既報の事故を示す。
2. その状況を既存方式だけでは扱えない理由を示す。
3. どの観測から着想を得たかを示す。
4. なぜその設計が必要だと判断したかを示す。
5. 実装、研究上の問い、貢献、評価範囲へ接続する。

出来事を並べるだけで終えない。各段落で「前の事実が、次の判断をなぜ必要にしたか」を書く。事故や個人的経験を劇的に盛らない。記録にない心情、会話、時系列、因果を補わない。

### 4. 手法を再現可能に書く

- 入力、処理、出力、比較対象、固定した条件、変えた条件を明示する。
- AI 評価では、実装版、モデル識別子、プロンプト、データまたはタスク集合、試行数、乱数性、選択手順、分母を記録する。確認できない項目は不明と書く。
- 評価指標を初出で定義し、その指標が測らないものも示す。
- トレース一件の評価、コンパイル済み policy 全体、タスク完了、安全性を同一視しない。

### 5. 結果を改善の鎖として書く

結果を書く前に [references/section-patterns.md](references/section-patterns.md) の「結果」を読む。各比較を次の順で記述する。

1. 基準実装と、その限界
2. 変更した実装箇所と変更内容
3. その変更が影響すると予想した仕組み
4. 指標名、定義、分母、評価条件
5. 変更前と変更後の値
6. 件数差と、率なら割合の差。「パーセントポイント」と呼ぶ場合は初出で意味を定義する
7. 統計的不確かさ、反復数、または一回測定であること
8. 何が良くなったか、何が悪化または不変だったか
9. その結果から言える範囲と言えない範囲
10. 原データまたは再現手順

単一指標の上昇だけを「改善」と呼ばない。たとえば不足なしが上がっても過剰なしが下がるなら、過不足なしを含めて併記する。対照実験がない場合は因果を断定せず、「観測した差」「実装差と整合する」と書く。ゼロ差、失敗した介入、採用しなかった案も隠さない。

### 6. 考察と限界を結果から分離する

- 結果節では観測値を示し、考察節では理由の解釈と次の検証を示す。
- 評価集合、版、模擬環境、選択方法、未測定の軸、欠けた対照条件を列挙する。
- 条件付き診断をタスク全体の成功率と呼ばない。計画生成失敗を都合よく分母から外さない。
- 実装の不変条件を、現実の配備全体に対する安全性保証へ拡張しない。

### 7. 人間の文章へ直す

事実の密度を保ちつつ、読み手が因果を追える文章へ直す。

- 段落ごとに一つの問いへ答える。主語と行為者を示す。
- 「重要である」「包括的である」「画期的である」のような根拠のない評価語を削る。
- 「まず、次に、最後に」の機械的な列挙、同じ長さの文の連続、毎段落末の決め台詞を避ける。
- 「本節では説明する」のような予告を削り、内容から始める。
- 三項目の定型列挙、過度な二項対立、同じ接続詞の反復を崩す。
- 抽象的な利点ではなく、誰が何をできるようになったか、どの失敗が何件減ったかを書く。

詳細な最終点検には [references/review-checklist.md](references/review-checklist.md) を読む。

### 8. 検証する

1. 次の監査を実行する。

```bash
python3 .agents/skills/write-pauth-paper/scripts/audit_pauth_paper.py <manuscript>
```

2. エラーをすべて直す。警告は文脈を確認し、残す場合は理由を説明する。
3. 主張台帳と専門語台帳を本文へ照合する。すべての数値について分母、版、条件、証拠位置を再確認する。
4. LaTeX を変更した場合は `paper/PAuthGateway` で `latexmk -pdf pauthgateway-template.tex` を実行し、ログと生成 PDF を確認する。Markdown を変更しても LaTeX のビルドだけでは検証にならない。
5. 図表を変更した場合は本文、表、図、キャプションの数値を相互照合する。
6. LLM 利用記録が必要な提出物では、実際に行った支援だけを記録する。存在しない雛形を参照しない。

## 完了条件

- すべての専門概念が正本にあり、初出で平易に定義されている。
- 「はじめに」の動機、着想、必要性に証拠または著者確認がある。
- 各主要結果が基準実装、変更、指標、差、利点、副作用、限界、証拠までつながっている。
- 中心的主張を原データまたは再現可能な結果まで追跡できる。
- 監査エラーがなく、未解決の警告と証拠不足を隠していない。
