# 章の組み立て方

## 目次

- 「はじめに」
- 結果
- 図表

## 「はじめに」

### 先に集める材料

次の空欄を証拠で埋める。空欄を想像で補わない。

| 材料 | 内容 | 出典 |
|---|---|---|
| 最初の観測 | 著者が困った具体的な状況、または確認済みの事故 | 記録、引用、著者確認 |
| 既存方式の限界 | 何を許せるが、どの粒度を表せないか | 仕様、先行研究、実装 |
| 着想のきっかけ | どの観測が設計案へ結び付いたか | ノート、履歴、著者確認 |
| 必要性 | 放置すると誰がどの失敗を受けるか | 脅威モデル、評価 |
| 研究上の問い | 何を比較し、何を測るか | 評価設計 |
| 貢献 | 実装したもの、測ったもの、分かったもの | 実装、結果 |

PAuth 固有の着想を探す場合は、スライドの発表原稿、設計文書、コミット履歴、issue、実験ログを候補にする。古い発表資料は物語の手掛かりにだけ使い、用語と数値を `docs/SYSTEM_MODEL.md` と原データで取り直す。

### 段落の役割

1. 読者が状況を再現できる具体例から始める。
2. 既存方式の不足を、対象、操作、粒度で特定する。
3. 著者が注目した関係を示す。
4. 設計判断を示し、その判断が前段の不足へどう対応するかを書く。
5. 研究上の問いと評価範囲を置く。

段落同士を「そして」でつながない。前段の制約が次の判断を必要にする因果を書く。

### 避ける形

- 「AI は急速に発展している」のような一般論から始める。
- 事故を挙げた直後に、提案方式がその事故を防ぐと飛躍する。
- 著者の動機を三人称で推測する。
- 「安全性は重要である」と書き、具体的な失敗を示さない。
- 最後に貢献を三つ並べるためだけに本文を組み立てる。

## 結果

### 一つの比較に必要な鎖

| 要素 | 書く内容 |
|---|---|
| 基準 | 比較前の実装版、設定、既知の限界 |
| 介入 | 変更したファイル、部品、規則、処理 |
| 仕組み | 変更がどの失敗へ影響すると予想したか |
| 測定 | 指標、分母、データ、試行数、固定条件 |
| 差 | 前値、後値、件数差、割合の差。パーセントポイントと記す場合は初出定義 |
| 分解 | 新たに成功した事例、失敗した事例、変化しなかった事例 |
| 価値 | 誰が何をできるようになったか |
| 代償 | 悪化した指標、費用、適用範囲、未測定項目 |
| 証拠 | 原データ、再現コマンド、版、ソース状態 |

### 執筆用の骨格

次の骨格へ事実を入れ、完成後に定型感が残らないよう文章をつなぎ直す。

> 基準実装 `<版>` は `<制約>` のため `<処理>` を扱えなかった。`<部品>` へ `<変更>` を加え、`<仕組み>` を扱えるようにした。`<評価集合>` の `<N>` 件を `<条件>` で測ると、`<指標>` は `<A/N>` から `<B/N>` へ `<件数差>` 件変化し、割合の差は `<率の差>` だった。差を生んだのは `<事例群>` である。`<別指標>` は `<変化>` したため、示せる利点は `<限定した結論>` であり、`<広い主張>` までは示さない。

「性能が向上した」で済ませない。実装差、観測差、解釈を別の文にする。

### AI 分野で追加する条件

- 比較する実装とモデルを分離する。モデルを変えた比較を実装改善だけの効果と呼ばない。
- プロンプト、候補選択、再試行、評価器、キャッシュ、温度、試行数の違いを記録する。
- 一回の確率的実行から分散を推定しない。
- 生成成功、クラッシュなし、トレース一致、タスク完了、安全性を一つの成功率へまとめない。
- 良くなった指標だけを抜き出さない。目的指標と対になる誤り方向を同じ表に置く。

### 因果の表現

- 対照条件と固定条件が揃う: 「変更により改善した」と書ける可能性がある。交絡を点検する。
- 実装差と測定差だけがある: 「変更後に差を観測した」「変更の狙いと整合する」と書く。
- 別実験、別モデル、別データ: 横に並べて因果比較しない。

## 図表

- キャプションだけで比較対象、指標、分母、条件が分かるようにする。
- 絶対数と率を混ぜない。率には分母を添える。
- 差を示す図では基準線と変更点を明示する。
- 本文、表、図の数値を同じ原データから生成または照合する。
- 手書き SVG を確定結果の正本にしない。生成元、結果ファイル、ハッシュを追える状態にする。
