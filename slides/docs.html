Self-hosted AI safety

PAuth Gateway

A task-scoped authorization proxy that sits in front of an unmodified AI agent. The user's prompt becomes a fixed allow-list of operations — derived once, enforced on every outward call. Built on the PAuth algorithm (Sharma et al., arXiv:2603.17170).

Zero FP / Zero FN reproduced Claude Code hook integration Default-deny enforcement Python 3.12+
01

Overview

PAuth Gateway is a local HTTP daemon that intercepts an AI agent's prompt and tool calls, derives an authorization plan from the user's original prompt, and then enforces that plan against every subsequent outward action. Nothing is installed inside the agent. The integration with Claude Code is a thin pair of hook scripts and a single line in settings.json.

The plan is constructed once, before the LLM reads any tool result. Any later context — whether from prompt injection, agent re-planning, or tool-output manipulation — cannot widen the plan. It can only fail to match.

Design stance

We do not trust the agent. We trust one thing only: the user's initial prompt, captured before the LLM sees it. Everything downstream is checked against a plan derived from that single trusted input.

02

The problem this solves

Today's agents protect users with two mechanisms, both of which fail in practice:

  • Up-front broad grants. The user OAuth-grants the agent a wide scope ("read all email", "send funds from this account") and trusts the model not to misuse it. A single prompt-injection in any retrieved context can convert that scope into damage.
  • Per-action approval prompts. The user is asked to confirm every sensitive call. After a few sessions the prompts blur together; the destructive ones look identical to the harmless ones. Approval-by-habit is the inevitable equilibrium, and major tools now ship a "skip permissions" flag for it.

Neither mechanism produces a boundary that survives an adversarial input or an attentive user's bad day. The gateway replaces both with a single, externally-fixed allow-list per task.

03

Approach

The gateway sits between the user and the agent, and between the agent and the world.

  user prompt ──► [ GATEWAY ] ──► agent  (plan fixed here, once)
                                  │
                                  ▼
                       tool calls ───► [ GATEWAY ] ──► SaaS / OS
                                       (every call checked
                                        against the fixed plan)

The plan is the structural artefact: a set of compiled rules describing which tool calls, with which operands, in which order, are part of fulfilling the user's request. It is generated by the PAuth pipeline (next section) and lives inside the gateway process. The agent never sees it, and cannot modify it.

Once the plan is fixed, the agent operates normally — same model, same tools, same prompts. The only difference is that every outward action is offered to the gateway, which permits it (if it matches a rule) or rejects it (if it doesn't).

04

Pipeline (A1 – B4)

The pipeline follows the paper's A/B partitioning. A1 is the only stage that uses an LLM. A2, A3, and the four B stages are fully deterministic.

StageRoleImplementation
A1Generate restricted-grammar code from the user promptpauth/codegen.py (LLM) + gateway/agentic_a1.py (grammar repair loop)
A2Derive NL slices from the generated codepauth/slicing.py (deterministic)
A3Compile slices into rules (Algorithm 1)pauth/rules.py (deterministic)
B1Default-deny on missing rulepauth/enforcer.py
B2Constant-operand matchingpauth/enforcer.py
B3Symbolic-operand resolution from the envelope storepauth/enforcer.py + pauth/evaluator.py
B4Guard evaluation (upstream-observation requirements)pauth/enforcer.py

The deterministic majority of the pipeline is the foundation of the zero false-permit result: if A1 produces grammar-valid code, the rest follows mechanically, and the boundary is reproducible across runs.

The restricted grammar

A1 may only emit straight-line code in a small subset (no loops, no list comprehensions, no method chains beyond a documented set). This restriction is what makes A2/A3 tractable and decidable. Any LLM output that exceeds the grammar is rejected outright by the parser (pauth/grammar.py), and the gateway either retries A1 with the violated rule fed back in (gateway/agentic_a1.py), or falls back to the recognizer-canonical path.

05

The gateway runs as a long-lived HTTP daemon on 127.0.0.1. Claude Code talks to it through two hook scripts — one for the user prompt, one for every tool call — keyed by Claude Code's own session_id.

06

Hard invariants

These are enforced by code, not by convention.

  1. Plan once. Gateway.submit_user_prompt is callable only once per session. A second prompt is structurally rejected at the channel. The gateway never re-plans based on agent input.
  2. Tool calls require a prior prompt. AgentChannel returns an error if a tool_call arrives before a prompt.
  3. Gateway is the observation authority. Permitted calls are executed by the gateway's suite runner, and results are recorded as HMAC-signed envelopes in a gateway-owned store. Operand verification reads from this store; agent-reported intermediate values are ignored.
  4. Default-deny. The enforcer denies any call without an exact-matching rule. Rejection reasons are surfaced verbatim for audit.
  5. Single signing root. The gateway owns the keyring. Envelopes are signed by the gateway, not by individual SaaS servers — trading the paper's per-server autonomy for a single deployable.
07

Threat model

What the gateway defends against

ThreatDefended by
Agent issues a tool call not in the user-derived planDefault-deny on missing rule (B1)
Agent substitutes a constant operand (recipient, amount, subject, date)Operand match against compiled rules (B2/B3)
Agent fabricates a derived value (e.g. cart.total it never observed)Symbolic eval against the envelope store; agent-reported values ignored (B3)
Agent skips an observation tool and uses its symbolic result anywayEnvelope missing → operand unresolved → denial
Agent calls a sensitive tool out of orderGuard evaluation requires upstream envelopes (B4)
Agent re-plans mid-session (e.g. on injection)AgentChannel rejects second PromptMessage
Tool-result prompt injection (AgentDojo threat model)Plan was generated before any tool output existed; injected actions are off-plan

Explicit non-goals

Out of scope

The gateway is an authorization layer, not a correctness oracle and not a comprehensive sandbox. Specifically it does not defend against:

ThreatWhy excluded
Injection embedded in the user's prompt itselfThe UI / input window is trusted; this is the user's responsibility.
Agent silently modifying the prompt while forwarding itUserPromptSubmit fires before the LLM sees the prompt, so the LLM cannot modify it. The hook itself is trusted.
Agent bypassing the hook (user disables it)The user is trusted to not disarm their own safety net.
Side channels (file system, child processes, env vars)The gateway sees tool calls only. A full Claude Code firewall needs additional bash and sandbox policy.
Prompt-intent correctness ("did the plan actually capture what the user wanted?")PAuth authorizes; it does not validate intent. The user can approve a plan that does the wrong thing — enforcement only guarantees the agent stays within that plan.
08

Claude Code integration

Two hook scripts and one daemon. The agent itself is unmodified.

1. Start the daemon

.venv/bin/python gateway/http_server.py --host 127.0.0.1 --port 8081

Leave it running. Restarting drops every active session.

2. Wire the hooks

Add to ~/.claude/settings.json (or the project-local .claude/settings.json):

{
  "hooks": {
    "UserPromptSubmit": [
      { "type": "command",
        "command": "/path/to/PAuthGateway/gateway/hooks/submit_prompt.sh" }
    ],
    "PreToolUse": [
      { "type": "command",
        "command": "/path/to/PAuthGateway/gateway/hooks/pretool.sh" }
    ]
  }
}

3. Choose enforcement mode

The scripts honour the following environment variables:

VariableValuesDefaultEffect
GATEWAY_URLURLhttp://127.0.0.1:8081Where to POST.
GATEWAY_MODE_PROMPTstrict / logstrictIf the gateway rejects the prompt, block Claude Code (strict) or log only (log).
GATEWAY_MODE_TOOLstrict / loglogSame for tool calls. Default is log during integration; flip to strict once the tool set is finalised.
GATEWAY_MODEstrict / log—Fallback when the more-specific variant is unset.
Failure modes to expect

Daemon down → hook prints an HTTP error; strict blocks, log allows.  |  Prompt outside the recognizer subset → gateway rejects; switch to freeform mode or extend the recognizer.  |  Tool not in the plan → pretool.sh reports REJECT.

Reproduced results

Measured with python -m experiment.run_experiment --suites all on GPT-4.1, AgentDojo v1 plus the paper's shopping suite:

Suite#FN (#injection runs)#FP (#benign runs)A1 skipped
shopping0 (8)0 (2)0
banking0 (135)0 (13)3
slack0 (51)0 (7)14
travel0 (32)0 (5)15
workspace0 (164)0 (22)18
Overall0 (390)0 (49)50

Zero false-positive and zero false-negative across every task where A1 generated grammar-valid code (49 benign + 390 forced-injection runs). This reproduces the central claim of the paper's Table 2.

A1 skipped counts tasks where GPT-4.1 emitted code outside the restricted grammar (loops, comprehensions, multiple assignment, etc.). These are rejected at the gate and never reach the enforcer — a conservative-by-construction failure mode, not a security one.

Honesty note

The experiment runner does not hard-code zero. If A1 emits faulty code, a false-positive appears; if a slice is wrong, a false-negative appears. The runner reports whatever actually happened in its ANOMALIES section. The zero/zero result above is measured, not asserted.

10

Limitations & roadmap

Known limitations

  • Ambiguous prompts. Implicit references ("send to my usual account") cannot be resolved deterministically. The strict path rejects them; the freeform path requires literal constants in the prompt. A clarification layer that prompts the user to disambiguate before plan derivation is the next planned addition.
  • Plan-intent correctness. The gateway authorises against the generated plan; it does not verify that the plan captures what the user meant. A second-model verification pass is under active iteration.
  • Adaptability to new agents / models. A1's prompt and grammar need retuning when the underlying model changes. A more systematic re-targeting mechanism is on the roadmap.
  • Single-user single-host topology. The current daemon assumes one user on one machine. Multi-user, multi-host, and persistent session state are deliberately deferred until the need becomes visible.
  • Side channels. The gateway observes tool calls only. Direct file-system access, subprocesses, or environment-variable reads bypass it. Closing those requires additional Bash policy and / or a sandbox.

Direction

Two principles drive the roadmap. First, expand only when forced to: each new feature ships when its absence is observed, not anticipated. Second, never let the LLM into the trusted core: A1 is and will remain the only non-deterministic stage.
