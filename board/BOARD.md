目的(不変): **エージェントにタスクを丸投げする安心感が得られるように、
権限自動化を行う仕組みを提供する。** それ以上でも以下でもない。

## 1. 現状の判断(2026-09-08、Claude Code 記)

出発点のリポジトリを読んだ上での事実と評価。事実と推測を分けて書く。

### できていること(事実)

- 執行の中核(Slicer・RuleCompiler・Enforcer・封筒)は決定的で、検査 502 件が
  通る。強制注入 2,440 件を全件拒否、良性タスクの過剰拒否 0(`eval.check`)。
- 計画は一度だけ、既定拒否、観測はゲートウェイが所有、送出前に実行試行を
  耐久化、という不変条件がコードで強制されている。
- HTTP デーモン(`gateway/serving/http_server.py`)に Bearer 認証・セッション
  永続化・監査 JSONL がある。
- Claude Code 向けの hook 二本(`gateway/hooks/`)、OS の外向き通信遮断
  (`gateway/deploy/egress_lockdown.sh`)、MCP(HTTP / stdio)と OpenAPI の
  ツールアダプタ、確認ゲート付きシンクがある。
- Planner の正解忠実度(過不足なし)は AgentDojo 97 タスクで 41/97(GPT-5.1、
  計画規則 T16 あり)。

### 実用の妨げになっていること(事実、重要度順)

1. **実ツールで端から端まで動いた記録がない。** 評価はすべてベンチマークの
   模擬スイート上。実 MCP サーバー + LLM Planner + 厳格モードで、実タスクを
   一件完走した記録がリポジトリにない。
2. **Planner の忠実度が半分以下。** 過不足なしが 41/97。実用では「正当な作業が
   止まる」(不足)か「頼んでいない範囲まで認可される」(過剰)が半数のタスクで
   起きる、ということ。計画生成の失敗(Fable 5 の安全分類器による拒否で空の
   計画が保存される等)も記録されている。
3. **Claude Code の内部ツール(Bash・Read・Edit 等)の扱いが未決。** 厳格モード
   では計画にないツールは全部拒否されるので、いまの hook 構成で厳格にすると
   Claude Code は使いものにならない。「外向きでないツールは素通し、外向き
   ツールはゲートウェイ経由」のような方針がコードにない。
4. **関門確認(一括確認)が本番経路に載っていない。** 汚染由来の制御オペランドを
   人間に確認させる機構は `eval/hitl.py` 専用。本番の `gateway/runtime/gateway.py`
   には昇格していない。設計判断は決まっている(下記「引き継ぐ設計判断」)。
5. **資格情報の仲介・利用者ごとのツール登録が未実装。** 実 SaaS を繋ぐ運用者の
   流れがない。
6. **hook の既定が観測のみ(`log`)。** 切り替えるまで執行は効いていない。
   hook が外れたことを検知する健全性検査もない。
7. 監査ログの回転、API 仕様変更時の再読み込み、提供元固有のエラー処理が未実装。

### 「安心感」の翻訳(推測、修正歓迎)

安心感 = 「丸投げしても、(a) 頼んでいないことは起きない、(b) 頼んだことは
止まらずに終わる、(c) どちらが起きたかを後から確かめられる」。
(a) は執行の中核が担い、すでに強い。(b) が弱い(忠実度と実ツール接続)。
(c) は監査ログがあるが、人間が読める形になっていない。
**いまの伸びしろは (b) にある。** (a) を測る指標だけを見て「安全」と言っても
安心感にはならない。

## 5. 引き継ぐ設計判断(既存の作業記録から。守ること)

これらは依頼主との過去の検討で確定した判断。Codex はこれを読まないと
知り得ないのでここに写す。

### 関門確認(2026-08-01 確定、T2 の実装契約)

1. 承認対象はデータではなく、**具体値入りの副作用ツール呼び出し**。
2. 関門は計画時ではなく **実行時・読み取り相の直後**。順序: Planner →
   コンパイル → 読み取り相 → 関門一回 → 書き込み相。計画前の読み取り素通しは
   しない。
3. 全オペランドが信頼済みの書き込みは関門**前**に実行してよい。要件は
   「割り込みゼロ」であって「承認まで世界を変えない」ではない。
4. 部分却下: 一件ずつ判断し、却下分だけ飛ばして残りは実行。「全部やめる」は
   UX に残す。
5. やり直しはゲートウェイ側で止めない・上限も設けない。新しい試みは毎回
   同じ関門を通る。
6. 却下フィードバックは値なしの定型文(`gateway/runtime/feedback.py`)を維持。
   汚染値をモデル文脈へ還流させない。
7. 関門の提示は値の一覧だけでなく出所付き。人間は「不明」の行は見抜くが、
   水増しされた評価値(決定の汚染)は見逃す。基準値や外れ値の印が要る。

### 用語・版番号

- DSL の版 G1/G2、Planner 版 P1〜P5 などの ID は凍結。失敗が確定した版だけ
  `P'1` のようにダッシュ化して保管し、番号は再利用しない。未確定のものを
  ダッシュ化しない。
- LLM 向けプロンプトの字面は版の定義そのものなので、改名で触らない。

### 計画生成失敗の既知の原因

- 計画なし 15 タスクの実態は、文法棄却ではなく Fable 5 の安全分類器
  (`stop_reason: refusal`、分類 `cyber`)による空応答。生成経路
  `_call_generator` が `stop_reason` を見ないため無記録で空キャッシュ化する。
  T4 の対象。

### 文法の強化には天井がある

- DSL に文字列演算を足して忠実度を上げようとしない(健全性を崩す)。残る壁は
  文字列整形・抽出で、これは関門確認で人間に確認させる経路で扱う。

### 再ベンチは必ず関門あり

- 依頼主にとって「再ベンチ」は、関門確認込み(人間が判断する)の実行を指す。
  関門なしの数値を「ベンチマーク結果」として報告しない。

## 6. 方向修正の記録

日付・記入者・理由・新しい方向を追記する。

- 2026-09-08 claude: 初版。方向性は上記 3 節。
- 2026-09-08 claude(方向修正 2): **Claude Code の hook 経路は、実 MCP を繋ぐと
  二重実行になる。** `PreToolUse` で許可された呼び出しはゲートウェイが自分の MCP
  接続で実行し、その後 Claude Code も自分の MCP 接続で同じ呼び出しを実行する。
  買い物デモ(模擬実行)では気付かない欠陥。よって Claude Code 向けの実用経路は
  「ゲートウェイを MCP サーバーとして Claude Code に登録し、実 MCP はゲートウェイの
  内側に置く」(T9)に変える。hook は (a) プロンプトの捕捉と (b) ローカルツールの
  方針(T3)に限定する。`docs/INGRESS_DESIGN.md` は「SDK 直結を先、傍受は後」と
  していたが、依頼主の目的(自分のエージェントに丸投げ)には無改変 Claude Code の
  経路が直結するので、順序を入れ替える。SDK 直結の契約は変えない。
- 2026-09-08 claude(判定基準の補足): K1 は「通過数」だけでなく「人間の承認なしで
  通過した数」を併記する。割り込みの回数は安心感の裏側(確認疲れ)の指標。
